Vite 8.3.6 در تاریخ ۵ نوامبر در [صفحه releases گیت‌هاب](https://github.com/vitejs/vite/releases) به‌عنوان Latest علامت خورد، دو هفته بعد از [8.3.5](/fa/blog/2026-10-22-vite-8-3-5-bundled-dev). [یادداشت‌های انتشار](https://github.com/vitejs/vite/releases/tag/v8.3.6) بخش امنیتی و advisory ندارد. با این حال سه مورد به حوزه‌های حساس امنیتی مربوط‌اند: فایل‌های `.wasm` خارج از `server.fs` حالا رد می‌شوند (#23914)، صفات HTML در سرور escape می‌شوند (#23995) و کدهای ANSI برای `server.forwardConsole` escape می‌شوند (#23933). من اول همین‌ها را می‌خواندم. بقیه یک پچ معمولی است: اصلاحات bundled dev، اصلاح optimizer و resolver و اصلاح هش chunk import map.

## تغییر `.wasm` و `server.fs`

سرور توسعه Vite فایل‌هایی را که سرو می‌کند محدود می‌کند. طبق [مستندات گزینه‌های سرور](https://vite.dev/config/server-options)، مقدار پیش‌فرض `server.fs.strict` برابر `true` است و با فعال بودن آن، درخواست برای فایلی خارج از فهرست `server.fs.allow` پاسخ 403 می‌گیرد، مگر اینکه یک فایل مجاز آن را import کند. اگر `allow` تنظیم نشده باشد، Vite دنبال ریشه workspace می‌گردد (فیلد `workspaces`، فایل `lerna.json` یا `pnpm-workspace.yaml`) و در غیر این صورت به ریشه پروژه برمی‌گردد. `server.fs.deny` فهرست مسدودسازی جداگانه‌ای است با پیش‌فرض‌هایی برای `.env*`، فایل‌های کلید و گواهی، `.npmrc`، `.yarnrc.yml` و `.git`، و بر `allow` اولویت دارد.

یادداشت انتشار فقط می‌گوید فایل‌های `.wasm` خارج از `server.fs` رد می‌شوند. نمی‌گوید پیش‌تر کدام مسیر اجازه عبور می‌داد و من PR را نخوانده‌ام، پس درباره سازوکار حدس نمی‌زنم. برداشت عملی این است که `.wasm` حالا تحت همان مرزی قرار می‌گیرد که سایر فایل‌های سروشده دارند.

این برای شما یعنی:

- اگر `.wasm` داخل ریشه پروژه یا ریشه workspace شناسایی‌شده باشد، چیزی تغییر نمی‌کند.
- اگر در پکیج هم‌سطح یک مونوریپو باشد که Vite آن را ریشه workspace نمی‌داند، یا در مسیری بیرون از آن، بعد از ارتقا در حالت توسعه انتظار 403 داشته باشید.
- اگر خودتان `server.fs.allow` را تنظیم کرده‌اید، طبق مستندات تشخیص خودکار خاموش است و فهرست باید محل wasm را صریحاً شامل شود.

راه‌حلی که تشخیص پیش‌فرض را نگه می‌دارد و مسیر خودتان را اضافه می‌کند:

```ts
// vite.config.ts
import { defineConfig, searchForWorkspaceRoot } from "vite";

export default defineConfig({
    server: {
        fs: {
            allow: [
                // keep Vite's workspace-root detection
                searchForWorkspaceRoot(process.cwd()),
                // the directory that holds your .wasm artifacts
                "../shared/wasm",
            ],
        },
    },
});
```

مستندات می‌گویند تنظیم `allow` تشخیص خودکار را غیرفعال می‌کند و برای حفظ آن `searchForWorkspaceRoot` را توصیه می‌کنند؛ قطعه کد بالا همین کار را می‌کند. برای ساکت کردن خطا `allow` را به یک مسیر خیلی گسترده تغییر ندهید؛ `allow` گسترده مرزی را که `server.fs.strict` برای اعمال آن وجود دارد، تضعیف می‌کند.

## escape کردن صفات HTML

یادداشت زیر حوزه server نوشته: «escape HTML attributes». سرور توسعه Vite در HTML بازنویسی و تزریق انجام می‌دهد، پس مقادیری که به صفات می‌رسند جای کلاسیک خروج یک نقل‌قول از صفت هستند. یادداشت‌ها نمی‌گویند کدام صفات یا کدام ورودی‌ها، پس نمی‌توانم بگویم آیا در عمل پیکربندی قابل سوءاستفاده‌ای وجود داشت یا نه. آنچه می‌شود با اطمینان گفت: بعد از ارتقا، مقادیر صفتی که قبلاً نقل‌قول یا براکت خام داشتند ممکن است متفاوت تولید شوند. اگر هوک سفارشی `transformIndexHtml` صفات را با الحاق رشته می‌سازد، smoke test حالت توسعه را دوباره اجرا کنید و HTML سروشده را ببینید. مسئولیت خروجی هوک شما در `vite build` همچنان با خودتان است و این مورد به آن اشاره‌ای ندارد.

## خروجی کنسول فوروارد‌شده

`server.forwardConsole` خطاهای مدیریت‌نشده و خروجی `console.error`/`console.warn` مرورگر را به ترمینال سرور توسعه می‌فرستد. طبق مستندات، پیش‌فرض آن خودکار است: اگر یک عامل کدنویسی هوش مصنوعی از طریق `std-env` شناسایی شود `true`، وگرنه `false`. این باعث می‌شود تغییر 8.3.6 مهم‌تر از ظاهرش باشد. رشته‌هایی که از مرورگر می‌آیند در ترمینالی چاپ می‌شوند که ممکن است یک عامل آن را بخواند، و کدهای ANSI خام در آن متن می‌توانند خطوط را رنگ‌بندی، بازنویسی یا پنهان کنند. escape کردن آن‌ها یعنی متن فقط متن دیده می‌شود. نمی‌گویم این جلوی prompt injection را می‌گیرد، چون یادداشت‌ها چنین ادعایی ندارند، اما دور نگه داشتن کدهای کنترلی از لاگ‌هایی که عامل می‌بیند یک خط پایه معقول است.

اگر رفتار را صریح می‌خواهید و نه مبتنی بر شناسایی:

```ts
export default defineConfig({
    server: {
        forwardConsole: {
            unhandledErrors: true,
            logLevels: ["error", "warn"],
        },
    },
});
```

گزینه‌های `unhandledErrors` و `logLevels` و مقادیر مجاز آن‌ها از همان صفحه مستندات آمده است.

## Bundled dev، بیلد و optimizer

دو مورد برچسب bundled dev دارند: import نام‌دار از ماژول‌های داخلی Node مجاز شد (#23858) و وقتی HMR نتواند یک entry را دوباره اجرا کند صفحه reload می‌شود (#23849). مورد دوم یک صفحه کهنه را با reload کامل عوض می‌کند که شکست ایمن‌تری است.

اصلاحات بیلد و chunk:

- امضای هش chunk import map از شناسه‌های پایدار ماژول استفاده می‌کند (#23976، رفع #23975). اگر از chunk import map استفاده می‌کنید، بعد از ارتقا دو بار بیلد بگیرید و یکسان بودن هش‌ها را بررسی کنید. شناسه‌های پایدار برای همین هدف‌اند، اما یادداشت‌ها سناریوی خرابی نمی‌دهند.
- importهای پویا با query الصاق‌شده هنگام جمع‌آوری وابستگی‌های CSS resolve می‌شوند (#23909).
- `build.sourcemap` وقتی از محیط تنظیم شود رعایت می‌شود (#23879).
- وقتی `build.ssr` برابر `true` است از `input` سطح بالا استفاده می‌شود (#23898).
- chunkی که با یک worker استفاده‌نشده تداخل دارد، اگر worker زنده هنوز از آن استفاده کند نگه داشته می‌شود (#23956).

Optimizer و resolver:

- optimizer پوشه cache را دقیق‌تر تشخیص می‌دهد (#23912).
- importهای زیرمسیر که با `#` شروع می‌شوند با resolver خود Vite حل می‌شوند (#23959)، ادامه کار `#` در 8.3.5.
- فایل‌هایی با query یا hash که با `new URL(..., import.meta.url)` ارجاع شده‌اند حالا watch می‌شوند (#23780).
- الگوهای `$` در جایگزینی aliasهای ایستا حفظ می‌شوند (#23703). اگر جایگزین alias شما `$&` یا مشابه آن دارد، این همان اصلاحی است که کم داشتید.

مرتبط با SSR: وقتی `ssr.target` برابر `webworker` است، فراخوانی‌های `require` خارجی به ماژول‌های داخلی به `import` تبدیل می‌شوند (#23759).

## کارایی

دو مورد: شنونده‌های لینک preload پس از settle شدن حذف می‌شوند (#23922، رفع #23920) و ماژول‌های رندرشده برای `cssScopeTo` به‌ازای هر خروجی یک بار ایندکس می‌شوند (#23889). عددی منتشر نشده است. اولی از نوع رفع نشتی است و فقط در صفحه‌های با preload زیاد اهمیت دارد؛ دومی بیلدهای با ماژول‌های CSS محدوده‌دار زیاد را تحت تأثیر قرار می‌دهد. پیش از ادعای بهبود، اندازه بگیرید.

## انتشارهای همراه

همان روز `plugin-legacy@8.2.4` منتشر شد که آن هم `build.sourcemap` محیطی را رعایت می‌کند، و `create-vite@9.3.4` که طبق یادداشتش وقتی ESLint استفاده شود TypeScript 6 را نگه می‌دارد. این ادامه رفت‌وبرگشت TypeScript 7 است که در [پست قبلی درباره create-vite](/fa/blog/2026-10-21-create-vite-typescript-7) آمده بود.

## چک‌لیست ارتقا

1. در یک شاخه ارتقا دهید و سرور توسعه را اجرا کنید. هر صفحه‌ای را که ماژول `.wasm` می‌گیرد یا نمونه‌سازی می‌کند باز کنید و دنبال 403 باشید.
2. در مونوریپو، محل artifactهای مشترک wasm را نسبت به ریشه workspace شناسایی‌شده بررسی کنید.
3. اگر تبدیل‌های HTML سفارشی دارید، HTML سروشده یک صفحه را با نسخه قبل مقایسه کنید.
4. اگر از chunk import map استفاده می‌کنید، دو بیلد production بگیرید و هش chunkها را مقایسه کنید.
5. سه مورد نزدیک به امنیت را سخت‌سازی بدانید، نه advisory تأییدشده. یادداشت‌ها آن‌ها را اصلاح امنیتی نمی‌نامند، پس در گزارش داخلی چنین ارجاعی ندهید.
