نسخهٔ [Nuxt v4.7.0](https://github.com/nuxt/nuxt/releases/tag/v4.7.0) در ۲۳ نوامبر منتشر شد؛ طبق [پست انتشار](https://nuxt.com/blog/v4-7) حدود ۳۵۰ کامیت بعد از 4.6.4. بیشترِ آن اختیاری یا آزمایشی است، اما چند مورد رفتار پیش‌فرض را عوض می‌کنند و یکی هم رفع امنیتی است که ممکن است بیرون از ریپوی شما اقدام بخواهد. این نوشته مواردی را مرور می‌کند که برای اپ‌های production مهم‌اند.

## اول این را انجام دهید: هشدار `_payload.json`

یادداشت‌های انتشار یک مشکل با شدت متوسط را فهرست می‌کنند: [GHSA-jxc9-w3j6-pwp2](https://github.com/nuxt/nuxt/security/advisories/GHSA-jxc9-w3j6-pwp2). اگر یک route rule فراگیر از نوع `cache`، `swr` یا `isr` با ruleی اختصاصی‌تر برای یک صفحه ترکیب شود، ممکن بود دادهٔ صفحهٔ یک کاربر کش شود و به کاربر دیگری برسد. حالت معمول، یک rule کش‌شدهٔ فراگیر به‌علاوهٔ `cache: false` روی بخش احراز هویت‌شده است:

```ts
export default defineNuxtConfig({
  routeRules: {
    "/**": { swr: 60 },
    "/account/**": { cache: false },
  },
});
```

ارتقا سرور را اصلاح می‌کند، اما چیزی را که قبلاً ذخیره شده پاک نمی‌کند. یادداشت‌ها توصیه می‌کنند اگر این ruleها صفحه‌های مخصوص کاربر را پوشش می‌دهند، هر CDN یا کش لبه‌ای که ممکن است فایل‌های `_payload.json` داشته باشد را پاک (purge) کنید.

همین نسخه یک رفع ناقص قبلی دربارهٔ اسلش‌های انکودشده در مسیرهای catch-all را کامل می‌کند ([GHSA-vrh2-cfcx-c3fg](https://github.com/nuxt/nuxt/security/advisories/GHSA-vrh2-cfcx-c3fg)، شدت متوسط؛ ruleهایی مثل `appMiddleware` روی `pages/[...slug].vue` را تحت تأثیر قرار می‌داد) و نشت کم‌اهمیت runtime config در سرور توسعه را هم رفع می‌کند ([GHSA-h5xj-x893-p5f7](https://github.com/nuxt/nuxt/security/advisories/GHSA-h5xj-x893-p5f7)). یادداشت‌ها می‌گویند چهار مورد رفع شده ولی سه مورد را فهرست می‌کنند و هشدارها در ۲۴ نوامبر منتشر می‌شوند؛ صفحهٔ هشدارها را دوباره ببینید.

## Nitro v3 با افزودن یک وابستگی

حالا می‌توانید اپ Nuxt 4 را روی Nitro v3 بسازید، پایهٔ Nuxt 5. پرچم پیکربندی وجود ندارد: `nitro` را به dependencies اضافه کنید تا Nuxt از آن استفاده کند؛ برای برگشت، حذفش کنید. انتشار آن را «بسیار آزمایشی» می‌نامد و توصیه می‌کند روی یک branch امتحان شود، نه production.

روی Nuxt 4، نسخهٔ v3 پشت یک لایهٔ سازگاری به نام `nitroLegacy` اجرا می‌شود که importهای `h3` و `nitropack`، auto-importهای v2، `useRuntimeConfig(event)`، `event.node` و hookهای v2 را سر پا نگه می‌دارد. وقتی همه‌چیز کار کرد، آن را خاموش کنید تا کدهایی که هنوز به آن تکیه دارند پیدا شوند:

```ts
export default defineNuxtConfig({
  nitroLegacy: false,
});
```

سه نقطهٔ شکست احتمالی:

- **wildcardها بیشتر match می‌کنند.** `/blog/*` حالا `/blog/2026/hello` را هم می‌گیرد. Nuxt برای هر ruleی که معنایش عوض می‌شود هشدار می‌دهد (`NUXT_B4029`). ruleی با چند wildcard، مثل `/api/*/items/**`، build را می‌شکند؛ آن را با پارامتر نام‌دار بازنویسی کنید: `/api/:id/items/**`.
- **matching مشترک است.** اپ route ruleها را مثل سرور match می‌کند، پس ruleهای مخصوص Nuxt (`appMiddleware`، `ssr`) روی همان مسیرها در هر دو سمت اعمال می‌شوند.
- **بازگشت به وابستگی‌های Nuxt نداریم.** اگر کد سرور پکیجی را import کند که در `package.json` شما نیست، `nuxt dev` با خطایی مثل `Cannot find package 'ufo'` می‌شکند. هر چه سرور import می‌کند را اعلام کنید.

اعداد منتشرشده (همان اپ، حدود ۱۷۰ صفحه، HTML یکسان): صفحهٔ اصلی از 926 به 1,236 req/s (+33%) و صفحه‌ای با 1,000 لینک از 219 به 316 req/s (+44%). یادداشت‌ها تنظیمات تست بار را شرح نمی‌دهند، پس این اعداد را جهت‌نما بدانید و روی مسیرهای خودتان اندازه بگیرید.

## `runtimeConfig` اعتبارسنجی‌شده

هر مقدار `runtimeConfig` حالا می‌تواند یک Standard Schema باشد (Zod، ArkType، Valibot):

```ts
import { z } from "zod";

export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: z.string(), // required at runtime
    public: {
      mode: z.enum(["preview", "production"]).default("production"),
    },
  },
});
```

متغیرهای محیطی هنگام شروع سرور به نوع schema تبدیل می‌شوند و اگر چیزی نبود یا نامعتبر بود، سرور با یک خطای `NUXT_E8014` که همهٔ مشکلات را فهرست می‌کند بالا نمی‌آید. schema هنگام build به توصیفی کوچک کامپایل می‌شود و در bundle سرور نمی‌رود. اعتبارسنجی‌های پشتیبانی‌شده فعلاً عمداً محدودند (نوع، مقدار الزامی، enum، union) تا شروع سرور سریع بماند؛ پس بررسی کنید قواعدی که به آن‌ها تکیه دارید جزو همین‌ها باشند.

این بر [نکتهٔ قبلی دربارهٔ runtimeConfig و متغیرهای محیطی](/fa/blog/2026-11-13-nuxt-runtime-config-env) بنا می‌شود: مقدار نادرست یا ناموجود حالا به‌جای بروز دیرتر، سرور را در boot متوقف می‌کند که برای orchestrator کانتینر مناسب است.

## `NuxtErrorBoundary` سمت سرور

با `experimental.ssrErrorBoundary` (در `compatibilityVersion: 5` فعال است)، `<NuxtErrorBoundary>` خطاهای حین رندر سرور را می‌گیرد. فرزند خراب، اسلات `#error` را در جای خودش رندر می‌کند، پاسخ 200 می‌ماند و کلاینت به همان حالت hydrate می‌شود. در production خطاهای غیر HTTP به‌صورت 500 ساده به اسلات می‌رسند تا پیام‌ها در HTML نشت نکنند.

```vue
<NuxtErrorBoundary retry-on-client>
  <template #error="{ error, clearBoundaryError }">
    <p>Recommendations are unavailable.</p>
    <button @click="clearBoundaryError">Retry</button>
  </template>
  <RecommendationsPanel />
</NuxtErrorBoundary>
```

`retry-on-client` فالبک را در HTML رندر می‌کند و سپس محتوای واقعی را در مرورگر دوباره امتحان می‌کند؛ جایگزین `<NuxtClientFallback>` است که منسوخ شد. prop اسلات `clearError` به `clearBoundaryError` تغییر نام داده تا تابع سراسری `clearError` را اشتباهی صدا نزنید، که boundary را خراب باقی می‌گذارد. بده‌بستان: پاسخ 200 همراه با فالبک، خطا را از پایش بر پایهٔ status code پنهان می‌کند، پس داخل boundary لاگ بگیرید.

## کارهای عملکردی

اعداد اصلی نسخهٔ v4.6.4 را با v4.7.0 روی اپ starter از بنچمارک‌های e18e و اپ‌های خود Nuxt مقایسه می‌کنند:

| معیار | 4.6.4 | 4.7.0 |
| --- | --- | --- |
| Server output (starter) | 2.17 MB | 1.23 MB |
| Initial page load (starter) | 80.4 kB, 14 requests | 66.3 kB, 3 requests |
| SSR throughput (starter) | 245 req/s | 292 req/s |
| Total blocking time (Nuxt UI landing page) | 276 ms | 180 ms |

زمان build روی اپ بزرگ حدود ۷٪ سریع‌تر و روی starter حدود ۶٪ کندتر است. تنظیمات تست بار فراتر از این شرح داده نشده. سازوکارها از خود اعداد مفیدترند:

- **`experimental.staticRoutes`** matcher مربوط به vue-router را یک بار می‌سازد، نه برای هر درخواست. نکته: `router.addRoute()`، `removeRoute()` و `clearRoutes()` خطا می‌دهند؛ مسیرها را از طریق hook به نام `pages:extend` اضافه کنید.
- **کلاینت سبک‌تر:** اگر چیزی از `$fetch` استفاده نکند `ofetch` حذف می‌شود و اگر کلاینت به head دست نزند، unhead. `<NuxtLink>`های داخلی ایستا در production به anchor ساده کامپایل می‌شوند.
- **Hydration:** V8 compile hint روی chunkهای entry، layout و page، با yield بین فازهای boot.
- **buildهای موازی:** `experimental.viteEnvironmentApi` کلاینت و سرور را هم‌زمان می‌سازد و `experimental.parallelBuild: false` اگر پلاگینی خروجی کلاینت را حین build سرور می‌خواند، آن را خاموش می‌کند.

## تجربهٔ توسعه

- **Template diagnostics** (به‌صورت پیش‌فرض روشن) دربارهٔ `<NuxtLink to="/abuot">` که با هیچ صفحه‌ای match نمی‌شود هشدار می‌دهد (`NUXT_B4025`) و نیز دربارهٔ `v-on`/`v-model` یا توابعی که به server component داده می‌شوند (`NUXT_B3014`، `NUXT_B3015`). لینک به مسیرهای سرور، فایل‌های `public/` یا سایت‌های دیگر به prop به نام `external` نیاز دارند.
- **نشانگر خطای dev** حالا خطاهای نوع، خروجی ESLint و هشدارهای کامپایلر Vue را هم جمع می‌کند. `typescript.typeCheck` مقدار `'dev'` یا `'build'` می‌پذیرد؛ اگر CI از قبل `nuxt typecheck` را اجرا می‌کند مفید است.
- **Nuxt CLI 4.1** خودش build production را رندر می‌کند و `nuxt dev --https` با HTTP/2 سرو می‌کند.
- **`@nuxt/rsbuild-builder`** (`builder: 'rsbuild'`) جایگزین `@nuxt/rspack-builder` منسوخ شد.

## WebMCP، آزمایشی

پشت `experimental.webmcp`، تگ JSDoc به نام `@tool` روی یک تابع آن را از طریق WebMCP، یک API پیشنهادیِ مرورگر، در اختیار عامل‌های هوش مصنوعی داخل مرورگر می‌گذارد. آرگومان‌ها از template می‌آیند، پس عامل فقط کاری را می‌تواند بکند که کاربر می‌تواند کلیک کند و دکمهٔ غیرفعال فعال نمی‌شود. مشخصات هنوز در حال تغییر است و در پیش‌نمایش اولیهٔ Chrome پشت یک پرچم قرار دارد؛ مرورگرهای دیگر چیزی ثبت نمی‌کنند و اپ مثل قبل رفتار می‌کند. جالب است، اما هنوز برای انتشار آماده نیست.

## چک‌لیست ارتقا

```sh
npx nuxt upgrade --dedupe
```

- Nuxt 4.7 به `vue` با نسخهٔ `^3.5.46` نیاز دارد؛ نسخه‌های قدیمی‌تر `NUXT_B7042` را فعال می‌کنند.
- `@nuxt/devtools` دیگر همراه Nuxt نصب نمی‌شود. اگر استفاده می‌کنید به `devDependencies` اضافه کنید.
- `globalThis.$fetch` فقط وقتی build استفاده را تشخیص دهد روی کلاینت نصب می‌شود. اگر از اسکریپت‌های inline یا فایل‌های `public/` صدایش می‌زنید، `experimental.globalFetch: true` را بگذارید.
- منتظر هشدارهای تازهٔ `NUXT_B4025` از template diagnostics باشید.
- اگر ruleهای `cache`، `swr` یا `isr` را با صفحه‌های مخصوص کاربر دارید، `_payload.json` را از هر CDN پاک کنید.

Nitro v3 را روی یک branch و ابتدا با `nitroLegacy` روشن امتحان کنید و پیش از آن بخش «Testing Nitro v3» راهنمای ارتقا را بخوانید.
