در ۷۲ ساعت گذشته چیز مهمی منتشر نشد. تنها انتشار این بازه [Vue 3.6.0-rc.17](https://github.com/vuejs/core/releases) بود که یک نسخهٔ کاندیدای انتشار است، و تازه‌ترین پست [وبلاگ Nuxt](https://nuxt.com/blog) هنوز Nuxt 4.7 مورخ ۲۳ نوامبر است که قبلاً پوشش داده‌ایم. نکتهٔ حرفه‌ای قبلی دربارهٔ Next.js بود، پس امروز نوبت Nuxt است، آن هم سمت سرور: کش Nitro.

همهٔ مطالب زیر با [راهنمای کش Nitro v2](https://v2.nitro.build/guide/cache) و [راهنمای کش فعلی Nitro](https://nitro.build/guide/cache) تطبیق داده شده است. این دو در چند جا با هم نمی‌خوانند و آن موارد را نشان می‌دهم، چون دردسر می‌سازند.

## اشتباه رایج

یک فراخوانی کند بالادستی را پشت هندلر کش‌شده می‌گذارید، بعد مسیر دغدغهٔ دوم پیدا می‌کند: «موارد ذخیره‌شدهٔ کاربرِ واردشده را هم نشان بده».

```ts [server/api/dashboard.get.ts]
export default defineCachedEventHandler(
    async (event) => {
        const user = event.context.user; // set by auth middleware
        const [stars, saved] = await Promise.all([
            $fetch("https://api.github.com/repos/nuxt/nuxt"),
            getSavedItems(user.id),
        ]);
        return { stars: stars.stargazers_count, saved };
    },
    { maxAge: 60 },
);
```

این کد از دو جهت غلط است و هر دو از نحوهٔ برخورد کش با درخواست می‌آیند.

1. **کش هدرهای درخواست را حذف می‌کند.** راهنمای v2 می‌گوید هنگام پردازش پاسخ‌های کش‌شده همهٔ هدرهای ورودی حذف می‌شوند و فقط آن‌هایی که در `varies` آمده‌اند در نظر گرفته می‌شوند. راهنمای فعلی همین را برای هدرها می‌گوید و اضافه می‌کند که کوکی‌ها و `authorization` مگر با `allowCookies` یا `allowAuthorization` حذف می‌شوند. پس هندلری که کاربر را از کوکی یا توکن تشخیص می‌دهد، در مسیری که طراحی نکرده‌اید آنچه را انتظار دارد نمی‌بیند.
2. **`event.context` با درخواست ورودی مشترک است.** راهنمای v2 صریحاً هشدار می‌دهد داده‌های هر کاربر را که از آن گرفته می‌شوند (مثلاً چیزی که میدلویر گذاشته) در هندلر کش‌شده رندر نکنید، چون برای درخواست‌های دیگر هم برگردانده می‌شود.

خطا بی‌صدا رخ می‌دهد: فهرست `saved` نخستین بازدیدکننده ۶۰ ثانیه کش می‌شود و با کد ۲۰۰ به بازدیدکنندهٔ بعدی داده می‌شود.

## الگوی بهتر: فراخوانی مشترک را کش کنید، نه مسیر را

بخش گران و مستقل از کاربر را به یک تابع کش‌شده ببرید و هندلر را بدون کش بگذارید.

```ts [server/utils/github.ts]
export const cachedRepoStars = defineCachedFunction(
    async (repo: string) => {
        const data = await $fetch<{ stargazers_count: number }>(
            `https://api.github.com/repos/${repo}`,
        );
        return data.stargazers_count;
    },
    {
        name: "repoStars",
        getKey: (repo: string) => repo,
        maxAge: 60 * 60,
        swr: true,
    },
);
```

```ts [server/api/dashboard.get.ts]
export default defineEventHandler(async (event) => {
    const user = event.context.user;
    const [stars, saved] = await Promise.all([
        cachedRepoStars("nuxt/nuxt"),
        getSavedItems(user.id),
    ]);
    return { stars, saved };
});
```

فراخوانی بالادستی مشترک و کش‌شده است، داده‌های کاربر همیشه تازه‌اند، و فهرست `saved` هیچ‌کس از راه کش نشت نمی‌کند چون هرگز وارد آن نمی‌شود. این ساختار از مثال راهنمای v2 پیروی می‌کند که تعداد ستارهٔ GitHub را با کلید repo کش می‌کند.

## گزینه‌هایی را که به آن‌ها تکیه دارید صریح بنویسید

چهار گزینه را هر بار بنویسید، چون پیش‌فرض‌ها کوچک‌اند یا بین دو راهنما فرق دارند.

- **`maxAge`** در هر دو راهنما پیش‌فرض `1` ثانیه است. بدون آن کشی دارید که تقریباً کش نمی‌کند. مقدار صریح `0` در راهنمای فعلی کش را غیرفعال می‌کند و آن راهنما می‌گوید همیشه صریح بنویسیدش.
- **`swr`**: راهنمای v2 پیش‌فرض `true` و راهنمای فعلی `false` ذکر می‌کند. اگر هر دو را بخوانید و متوجه نشوید، قضاوتتان دربارهٔ اینکه کاربر مقدار کهنه می‌بیند یا نه غلط می‌شود. صریح بنویسیدش.
- **`staleMaxAge`**: در راهنمای فعلی، `swr: true` بدون آن TTL نمی‌نویسد و ورودی‌ها تا زمان حذف می‌مانند. در راهنمای v2 پیش‌فرض `0` و غیرفعال است. اگر مقدار کهنه باید سقف داشته باشد، تنظیمش کنید.
- **`name` و `getKey`**: در v2، `name` پیش‌فرض نام تابع یا `_` است و `getKey` هش آرگومان‌هاست. راهنمای فعلی هشدار می‌دهد توابعی که با کارخانه یا حلقه ساخته می‌شوند و کد یکسان دارند، اگر `name` یا `getKey` صریح نداشته باشند ورودی‌های هم را بازنویسی می‌کنند. اگر توابع کش‌شده را در حلقه می‌سازید، مثلاً برای هر tenant یا هر upstream، به آن‌ها نام بدهید.

برای هندلری که واقعاً عمومی است، `varies` راه گفتن این است که کدام هدرها ورودی‌ها را جدا می‌کنند. مثال v2 از `varies: ['host']` استفاده می‌کند. در راهنمای فعلی `varies`، `allowQuery`، `allowCookies` و `allowAuthorization` دکمه‌های کار هستند و query string حذف می‌شود مگر `allowQuery` نام‌ها را فهرست کند. یک `/api/search?q=...` کش‌شده که `q` را نادیده می‌گیرد، یک نتیجه را برای همه برمی‌گرداند؛ پس پیش از کش کردن هر چیزِ پارامتردار ببینید خط Nitro شما با query string چه می‌کند.

## ابطال و محل ذخیرهٔ ورودی‌ها

در Nitro v2 با حذف کلید ذخیره‌سازی باطل می‌کنید. شکل کلید در راهنما `${group}:${name}:${getKey(...)}.json` است و نویسه‌های غیرکلمه‌ای حذف می‌شوند؛ پس تابعی به نام `getAccessToken` با `getKey: () => "default"` در `nitro:functions:getAccessToken:default.json` قرار می‌گیرد:

```ts
await useStorage("cache").removeItem("nitro:functions:repoStars:nuxtnuxt.json");
```

به اسلش حذف‌شده در این کلید دقت کنید: `nuxt/nuxt` به `nuxtnuxt` تبدیل می‌شود. همین نرمال‌سازی یعنی دو مقدار متفاوت `getKey` می‌توانند برخورد کنند، که راهنما آن را در هشدارها آورده است. مثال خود راهنما برای `/api/products/sale-items` پیشوند group و name را ندارد و با الگوی بیان‌شده نمی‌خواند؛ یک بار کلیدهای ذخیره‌سازی را فهرست کنید و کلید واقعی را کپی کنید، به رشتهٔ دست‌ساز اعتماد نکنید.

راهنمای فعلی این کار را به خود تابع می‌برد: `.invalidate()` و `.expire()` را روی `defineCachedFunction` می‌دهد و می‌گوید هندلرهای کش‌شده را نمی‌توان بر حسب نیاز باطل کرد. اگر دکمه‌ای می‌خواهید که داده را تازه کند، این هم دلیلی است برای کش کردن تابع به‌جای هندلر.

ذخیره‌سازی جزئیات عملیاتی دیگر است. در v2 محیط تولید به‌طور پیش‌فرض از درایور حافظه استفاده می‌کند، پس ورودی‌ها مخصوص هر فرایندند و با راه‌اندازی مجدد از بین می‌روند، و درایور توسعه فایل‌سیستم است. برای اشتراک کش بین چند نمونه، یک درایور را روی `storage.cache` سوار کنید؛ راهنما Redis را نشان می‌دهد. راهنمای فعلی `memory` را یک LRU درون‌فرایندی با سقف ۱۰۰۰۰ ورودی و ۱۰۰ مگابایت توصیف می‌کند و هشدار می‌دهد درایور `kv` سقف پیش‌فرضی برای اندازهٔ بدنه ندارد، پس روی مسیرهایی که پاسخ‌های بزرگ بالادستی را پروکسی می‌کنند `maxBodySize` بگذارید.

## بده‌بستان‌ها

- تابع کش‌شده یک مسیر کد دیگر برای فکر کردن اضافه می‌کند. اگر محاسبه ارزان است یا مقدار در هر درخواست عوض می‌شود، رهایش کنید.
- `swr: true` با دادن داده کهنه تأخیر را پنهان می‌کند. برای تعداد ستاره خوب است و برای قیمتی که از کاربر کسر می‌کنید غلط.
- فقط `GET` و `HEAD` کش می‌شوند و پاسخ‌هایی با `set-cookie` یا `cache-control` برابر `private`، `no-store` یا `no-cache` ذخیره نمی‌شوند. هندلری که کوکی نشست می‌گذارد هرگز کش نمی‌شود؛ معمولاً درست است ولی کسانی را که انتظار دیگری داشتند غافلگیر می‌کند.
- مقدارهای بازگشتی JSON می‌شوند، پس `Map`، `Set` و symbol در رفت‌وبرگشت از بین می‌روند.

## کجا هندلر کش‌شده هنوز درست است

مسیر کاملاً عمومی که پاسخش فقط به path بستگی دارد، مثل یک فید رندرشده یا بخشی از sitemap، برای `defineCachedEventHandler` یا قاعدهٔ مسیر `cache` مناسب است. مرز ساده است: اگر بخشی از پاسخ به اینکه چه کسی می‌پرسد بستگی دارد، تابع مشترک زیر آن را کش کنید و هندلر را بدون کش بگذارید.
