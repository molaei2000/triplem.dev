هفدهم نوامبر تیم Next.js مطلب [How we're using AI to make Next.js more secure](https://nextjs.org/blog/how-were-using-ai-to-make-nextjs-more-secure) را منتشر کرد. بخشی از آن توضیح روندی است که احتمالاً در صف ارتقاهای خودتان حس کرده‌اید، و بخشی دیگر معرفی ابزاری است که نحوه‌ی گرفتن patchها را تغییر می‌دهد. هر دو بخش روی نحوه‌ی نگهداری یک اپ Next.js در production اثر می‌گذارند.

## عددها و توضیح تیم

مطلب تعداد advisory در هر سال را می‌آورد: ۶ مورد در ۲۰۲۴، ۱۴ مورد در ۲۰۲۵ و تا امروز ۵۱ مورد در ۲۰۲۶. برداشت تیم این است که هوش مصنوعی یافتن و بهره‌برداری از آسیب‌پذیری‌ها را ارزان کرده؛ پس باگ‌هایی که قبلاً حالت‌های لبه‌ی غیرعملی بودند حالا ارزش رفع شدن دارند. داده‌ی پشتیبان: از ۵۱ مورد امسال، ۷۰٪ در کدی بودند که دست‌کم یک سال از عمرش گذشته، و ۴۳٪ در کدی با سه سال سابقه یا بیشتر. فقط ۳۰٪ از کدی با کمتر از یک سال سن آمده بود.

این تحلیل خود تیم درباره‌ی کدبیس خودشان است، نه ممیزی مستقل. با این حال چارچوب مفیدی است: افزایش یعنی فریم‌ورک در ۲۰۲۶ بدتر نشده، بلکه یک انباشت باگ دارد تخلیه می‌شود. مطلب همچنین می‌گوید بسیاری از مشکلات جدی‌تر از وابستگی‌های بالادستی آمده‌اند، به‌ویژه کتابخانه‌های تصویری پشت image optimization، نه از کد خود Next.js.

## آنچه تیم از سمت خودش تغییر داد

سه اقدام برای انبار باگ‌های قدیمی:

- برنامه‌ی bug bounty، تا گزارش خصوصی از بهره‌برداری سودآورتر باشد.
- یک بات داخلی ساخته‌شده با Eve برای triage گزارش‌ها، ساخت reproduction، تأیید شدت و بررسی کامل بودن رفع.
- ممیزی دستی Trail of Bits که مواردی را پیدا کرد که منابع دیگر از دست داده بودند.

دو اقدام برای کد جدید:

- یک agent بازبینی خصمانه (Security Review در Vercel Agent) روی هر pull request اجرا می‌شود و با دستورالعمل‌های سفارشی سعی می‌کند از تغییر سوءاستفاده کند. مطلب می‌گوید مواردی را گرفته که CI سبز و بازبینی موفق داشتند.
- مستحکم‌سازی مرزهای سرویس. ناهماهنگی بین لایه‌ها (proxy، CDN، runtime) می‌تواند منشأ bypass باشد؛ پس تیم این درزها را با Adapters رسمی می‌کند، یعنی قراردادی که می‌گوید میزبان‌ها چطور باید اپ Next.js را سرو کنند.

درباره‌ی وابستگی‌ها، تیم می‌گوید image optimization را به سمت codecهای memory-safe می‌برد و از هوش مصنوعی برای نمونه‌سازی سریع یکپارچه‌سازی و sandbox استفاده می‌کند. جزئیات بیشتر را بعداً وعده داده‌اند، پس این را جهت‌گیری بدانید، نه رفتار منتشرشده.

## ریتمی که حالا باید با آن برنامه‌ریزی کنید

انتشارهای امنیتی حالا تقریباً ماهانه‌اند و از قبل اعلام می‌شوند تا میزبان‌ها پیش از علنی شدن جزئیات محافظت اضافه کنند. [فهرست بلاگ Next.js](https://nextjs.org/blog) این ریتم را نشان می‌دهد: اعلام «Upcoming» حدود یک هفته پیش از هر انتشار (مثلاً ۲۷ اکتبر برای انتشار ۳ نوامبر)، و به‌روزرسانی‌های خارج از نوبت وقتی مشکل بالادستی بحرانی است (۲۲ سپتامبر و ۱۴ اکتبر).

برای یک تیم، این یعنی patch کردن از واکنش به حادثه به یک فرایند ثابت تبدیل می‌شود. اگر پایپ‌لاین شما ارتقای Next.js را کاری فصلی می‌داند، این حساب دیگر جواب نمی‌دهد.

## هشدار نسخه در `next dev` و `next build`

از Next.js 16.4، دستورهای `next dev` و `next build` می‌گویند نسخه‌ی نصب‌شده تحت تأثیر یک آسیب‌پذیری شناخته‌شده است. در توسعه، DevTools بخش Vulnerability Insight را با یک prompt نشان می‌دهد که می‌توانید در agent کدنویسی‌تان paste کنید. یادآور تعاملی سه گزینه دارد: ارتقا همین حالا، رد کردن، یا رد کردن تا نسخه‌ی بعد.

[راهنمای agent upgrade](https://nextjs.org/docs/app/guides/upgrading/agent-upgrade) تنظیمات را شرح می‌دهد. یادآورها به‌طور پیش‌فرض با سیاست `security` روشن‌اند و سیاست دیگر را در `next.config.ts` انتخاب یا آن‌ها را خاموش می‌کنید:

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
    experimental: {
        agentUpgrade: "latest", // or "security", "experimental-future", or false
    },
};

export default nextConfig;
```

دو نکته در عمل مهم است. یادآور هرگز خودش چیزی را ارتقا نمی‌دهد. و در ترمینال تعاملی، `next dev` یا `next build` تا وقتی پرسش باز است ادامه می‌دهد و اگر رد کنید خروجی بافرشده را دوباره پخش می‌کند.

## `next upgrade --agent`

مطلب و راهنما دستوری را شرح می‌دهند که ارتقا را به یک agent کدنویسی می‌سپارد:

```bash
npx next@canary upgrade --agent
```

طبق راهنما، ابتدا نسخه‌ی نصب‌شده، metadata انتشار و داده‌ی امنیتی لازم برای سیاست را بررسی می‌کند و اگر ارتقایی لازم نباشد یا هدفی تعیین نشود، با توضیح متوقف می‌شود. در غیر این صورت راهنماهای مهاجرت و Skills مرتبط را در یک پوشه‌ی موقت کپی می‌کند و یک task برای agent می‌سازد. این task از agent می‌خواهد کار تکراری نکند، در صورت امکان از یک Git worktree جدا استفاده کند، بررسی‌های مربوط را اجرا کند و نتیجه را تأیید کند.

سیاست‌ها:

| سیاست                 | رفتار                                                                        |
| --------------------- | ---------------------------------------------------------------------------- |
| `security`            | برای نسخه‌ی پایدار آسیب‌پذیر، آخرین نسخه‌ی امن در کهن‌ترین major مجاز         |
| `latest`              | اپ را به آخرین نسخه‌ی پایدار npm می‌برد (یا اپ canary را به `canary`)          |
| `experimental-future` | `latest` به‌علاوه‌ی پذیرش پیش‌فرض‌های برنامه‌ریزی‌شده مثل Cache Components     |

سیاست `security` جالب‌ترین است: مطلب می‌گوید در کهن‌ترین major دارای رفع می‌ماند، پس patch شما را به مهاجرت major مجبور نمی‌کند. `--agent` را نمی‌شود با `--revision` ترکیب کرد، برای App Router و Pages Router کار می‌کند و اگر داخل یک agent اجرا شود، task را برای همان agent چاپ می‌کند. در ترمینال تعاملی می‌تواند نشست Codex یا Claude Code نصب‌شده را شروع کند.

## نکته‌ها و محدودیت‌ها

- راهنمای agent upgrade برچسب **Experimental** دارد و می‌گوید برای production توصیه نمی‌شود. استفاده از آن برای آماده کردن PR وصله در یک worktree با اجرای بدون نظارت روی شاخه‌ی production ریسک متفاوتی دارد.
- راهنما برای گرفتن آخرین ابزار ارتقا حتی روی Next.js قدیمی‌تر از `npx next@canary` استفاده می‌کند. این یک انتخاب آگاهانه‌ی ابزار canary است؛ پس نسخه‌ی خود اپ را با lockfile ثابت نگه دارید و diff را مثل هر تغییر وابستگی بازبینی کنید.
- وقتی agent یک patch امنیتی را اعمال می‌کند، باز هم باید راستی‌آزمایی شود. task از agent می‌خواهد بررسی‌ها را اجرا کند، اما گیت واقعی تست‌های خودتان و بازبینی انسانی diff است.
- تعداد advisoryها و درصدهای سن کد را تیم Next.js درباره‌ی پروژه‌ی خودش گفته است. مطلب روش‌شناسی را شرح نمی‌دهد، پس آن‌ها را برای جهت‌گیری به کار ببرید، نه به‌عنوان benchmark.

## با این اطلاعات چه کنیم

1. مشخص کنید چه کسی مالک patch ماهانه‌ی Next.js است و اعلان‌های «Upcoming security release» را دنبال کنید.
2. مطمئن شوید کسی خروجی `next build` در CI را می‌خواند. هشدار جدید فقط وقتی کمک می‌کند که دیده شود.
3. تست‌هایی داشته باشید که بتوانند patch را سریع اعتبارسنجی کنند، چون مسیر ارتقای سریع‌تر فقط با راستی‌آزمایی سریع ارزش دارد.
4. `next upgrade --agent` را پیش از نیاز روی یک شاخه امتحان کنید، تا بار اول وسط یک حادثه نباشد.
5. مسیرهای پردازش تصویر خودتان را بررسی کنید. اگر مشکلات جدی در کتابخانه‌های بالادستی بوده، تغییرات codec را که تیم وعده داده دنبال کنید.
