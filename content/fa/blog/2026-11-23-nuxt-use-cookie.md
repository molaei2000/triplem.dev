در ۷۲ ساعت گذشته چیز پایدار و مهمی منتشر نشده است. آخرین نسخه پایدار Vue برابر 3.5.46 است و 3.6.0-rc.16 هنوز پیش‌انتشار است، Vite فقط یک بتای 8.4 دارد، Node.js یک نسخه آلفای 27 و وصله‌های LTS منتشر کرده و جدیدترین انتشار Nuxt هنوز وصله امنیتی 4.6.4 است. کاندیدای انتشار و وصله‌ها ارزش یک پست ندارند، پس امروز یک نکته درباره Nuxt می‌نویسیم: کامپوزبلی که ساده به نظر می‌رسد ولی چند گزینه دارد که اغلب روی پیش‌فرض می‌مانند: `useCookie`.

## اشتباه رایج

کاربرد معمول، تنظیمی است که سرور باید پیش از اولین رندر بداند: تم، زبان، یا بنری که کاربر بسته است. اشتباه این است که آن را در `localStorage` یا یک ref فقط‌کلاینتی نگه دارند که سرور نمی‌بیند. صفحه با مقدار پیش‌فرض رندر می‌شود، هیدرات می‌شود و بعد تغییر می‌کند. `useCookie` دقیقاً برای همین ساخته شده، چون کوکی همراه درخواست می‌آید و سرور می‌تواند با مقدار واقعی رندر کند.

```vue
<script setup lang="ts">
// Wrong: the server never sees this, so SSR always renders "dark"
const theme = ref("dark");
onMounted(() => {
    theme.value = localStorage.getItem("theme") ?? "dark";
});
</script>
```

```vue
<script setup lang="ts">
// Right: SSR reads the request cookie, the client reads document.cookie
const theme = useCookie<"dark" | "light">("theme", {
    default: () => "dark",
    maxAge: 60 * 60 * 24 * 365,
    sameSite: "lax",
});
</script>

<template>
    <button @click="theme = theme === 'dark' ? 'light' : 'dark'">{{ theme }}</button>
</template>
```

بر اساس [مستندات useCookie](https://nuxt.com/docs/4.x/api/composables/use-cookie)، این کامپوزبل یک `Ref` در Vue برمی‌گرداند که روی سرور و کلاینت کار می‌کند: انتساب به `.value` کوکی را می‌نویسد و خواندن آن مقدار فعلی را برمی‌گرداند. مقادیر به‌صورت JSON سریالایز می‌شوند و کامپوزبل فقط داخل کانتکست Nuxt کار می‌کند.

## تله اول: watch عمیق است، نه سطحی

گزینه `watch` مقدارهای `true`، `false` یا `'shallow'` را می‌پذیرد و پیش‌فرض آن `true` است، یعنی واچ عمیق. وقتی کوکی یک آبجکت یا آرایه نگه می‌دارد این اهمیت پیدا می‌کند. با پیش‌فرض، تغییر یک پراپرتی تو در تو کوکی را دوباره می‌نویسد. اگر `watch: 'shallow'` بگذارید فقط تغییرهای سطح بالا دنبال می‌شوند، پس یک `push` تا وقتی مقدار را دوباره انتساب ندهید ذخیره نمی‌شود.

```ts
const list = useCookie<number[]>("list", {
    default: () => [],
    watch: "shallow",
});

function add(n: number) {
    list.value?.push(n); // not saved yet with 'shallow'
}

function save() {
    list.value &&= [...list.value]; // reassignment: saved
}
```

مستندات این را به‌عنوان نمونه واچ سطحی آورده‌اند. مصالحه این است که واچ عمیق با هر تغییر تو در تو دوباره سریالایز می‌کند، در حالی که حالت سطحی کنترل زمان نوشتن را به شما می‌دهد، به قیمت اینکه ممکن است انتساب دوباره را فراموش کنید. و `watch: false` راهی است برای خواندن کوکی بدون اینکه تغییرهای واکنشی هرگز آن را بنویسند.

## تله دوم: readonly با watch: false یکی نیست

`readonly: true` همه نوشتن‌ها را در سرور و کلاینت مسدود می‌کند و مستندات می‌گویند مقدار `default` همچنان برگردانده می‌شود اما هرگز ذخیره نمی‌شود. `watch: false` فقط جلوی نوشتن ناشی از تغییرهای واکنشی را می‌گیرد. اگر کوکی‌ای می‌خواهید که فقط ورودی باشد، مثل یک فلگ که سیستم دیگری می‌گذارد، `readonly` این قصد را بیان و اجرا می‌کند.

```ts
const flags = useCookie("flags", {
    readonly: true,
    default: () => ({ beta: false }),
});
```

## تله سوم: secure و httpOnly در برابر هیدریشن

دو گزینه تعیین می‌کنند چه کسی کوکی را می‌خواند و هر دو در مستندات به‌عنوان خطر هیدریشن ذکر شده‌اند:

- `secure: true` کوکی را به HTTPS محدود می‌کند. مستندات هشدار می‌دهند که سرو صفحه روی HTTP ساده می‌تواند خطای هیدریشن بسازد، چون مرورگر کوکی را پس نمی‌فرستد. این مشکل در توسعه محلی روی HTTP و در محیط‌های staging بدون TLS پیش می‌آید.
- `httpOnly: true` کوکی را از جاوااسکریپت سمت کلاینت پنهان می‌کند. اگر کلاینت به مقدار نیاز داشته باشد، هیدریشن می‌تواند ناهمخوان شود، چون سرور آن را دیده و مرورگر نمی‌تواند.

قاعده عملی این است که تصمیم بگیرید مالک کوکی کدام طرف است. تنظیمی که هم رندر سرور و هم کد کلاینت می‌خوانند باید کوکی ساده و بدون `httpOnly` باشد. توکن نشست متعلق به سرور است: آن را از یک route در Nitro با کمک‌های h3 بگذارید، جایی که `httpOnly` طبیعی است، و هرگز از طریق کامپوزبل کلاینت در دسترس قرار ندهید. مستندات نمونه سمت سرور را هم نشان می‌دهند:

```ts
// server/api/counter.get.ts
export default defineEventHandler((event) => {
    let counter = getCookie(event, "counter") || 0;
    setCookie(event, "counter", ++counter);
    return { counter };
});
```

## تله چهارم: انقضا خودبه‌خود تمدید نمی‌شود

انقضا به‌صورت خودکار تمدید نمی‌شود. باید به `.value` انتساب بدهید. از نسخه 4.4 گزینه `refresh` وجود دارد: با `refresh: true` هر انتساب صریح انقضا را تمدید می‌کند، حتی اگر مقدار تغییر نکرده باشد. این یک نشست لغزان می‌دهد بدون اینکه مقدار ساختگی بسازید.

```ts
const visit = useCookie("visit", {
    maxAge: 60 * 60,
    refresh: true,
    default: () => "active",
});

visit.value = "active"; // same value, but the one-hour window restarts
```

دو نکته دیگر از مستندات. اگر هم `expires` و هم `maxAge` را بگذارید، بعضی کلاینت‌ها `expires` را نادیده می‌گیرند، پس هر دو را به یک زمان برسانید یا فقط از `maxAge` استفاده کنید. و `expires` می‌تواند تابعی باشد که در هر نوشتن اجرا می‌شود، پس آن را بدون عارضه جانبی نگه دارید.

```ts
const token = useCookie("token", {
    expires: () => new Date(Date.now() + 60 * 60 * 1000),
});
```

## تله پنجم: تغییرهای جای دیگر دیده نمی‌شوند

وقتی واچ فعال است، ref تغییرهای شما را در کوکی می‌نویسد اما تغییرهایی را که جای دیگر رخ می‌دهند، مثل تب دیگر یا کد سرور، متوجه نمی‌شود. مستندات برای بارگیری دوباره مقدار از کوکی به `refreshCookie` اشاره می‌کنند. اگر دو تب می‌توانند یک تنظیم را عوض کنند، آن را روی رویداد visibility یا focus صدا بزنید و فرض نکنید ref همیشه به‌روز است.

## تله ششم: کدگذاری سفارشی

به‌طور پیش‌فرض مقدار هنگام نوشتن از JSON و `encodeURIComponent` می‌گذرد و هنگام خواندن از `decodeURIComponent` و destr. می‌توانید `encode` و `decode` خودتان را بدهید. اگر `decode` خطا بدهد، رشته خام کوکی برگردانده می‌شود، پس کوکی خراب یا دستکاری‌شده حتی وقتی ref را آبجکت تایپ کرده‌اید به‌صورت رشته به کد شما می‌رسد. پیش از اعتماد اعتبارسنجی کنید:

```ts
const prefs = useCookie<{ density: "compact" | "roomy" }>("prefs", {
    default: () => ({ density: "roomy" }),
});

const density = computed(() =>
    typeof prefs.value === "object" && prefs.value?.density === "compact" ? "compact" : "roomy",
);
```

بازگشت به رشته خام در مستندات آمده است و اعتبارسنجی بالا یک الگوی دفاعی روی آن است، نه چیزی که مستندات توصیه کرده باشند.

## وقتی الگوی اولیه درست است

اگر مقداری فقط بعد از هیدریشن استفاده می‌شود و هرگز روی مارک‌آپ اثر ندارد، مثل موقعیت اسکرول یا پیش‌نویس یک فیلد متنی، `localStorage` ساده‌تر است و به هر درخواست بایت اضافه نمی‌کند. کوکی‌ها با هر درخواست به مسیر منطبق می‌روند و این هزینه دیده شدن توسط سرور است. مستندات حد اندازه‌ای ذکر نکرده‌اند، پس حجم را کم نگه دارید و شناسه یا enum کوتاه ذخیره کنید، نه داده‌های بزرگ.

## چک‌لیست

1. آیا سرور برای رندر درست به مقدار نیاز دارد؟ از `useCookie` با `default` استفاده کنید.
2. آیا آبجکت است؟ بین عمیق (پیش‌فرض) و `'shallow'` تصمیم بگیرید و بدانید کدام تغییرها ذخیره می‌شوند.
3. آیا برنامه نباید آن را تغییر دهد؟ از `readonly` استفاده کنید.
4. آیا راز است؟ آن را سمت سرور با `httpOnly` بگذارید، نه با `useCookie` در کلاینت.
5. آیا پنجره لغزان می‌خواهد؟ از `refresh: true` استفاده کنید و هنگام فعالیت انتساب بدهید.
6. آیا تب دیگر می‌تواند آن را عوض کند؟ فراخوانی `refreshCookie` را برنامه‌ریزی کنید.
