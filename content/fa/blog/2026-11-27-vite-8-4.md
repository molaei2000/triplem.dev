Vite 8.4.0 در ۲۶ نوامبر منتشر شد، پس از دو نسخهٔ بتا (۱۶ و ۲۵ نوامبر). برخلاف جریان پچ‌های 8.3.x، این یک نسخهٔ minor با تغییرات واقعی است: لایهٔ دوم محافظت از فایل‌ها در dev server، یک API جدید برای هر environment، رسیدن bundled dev mode به SSR، و چند حذف و تغییر نام که می‌توانند config را بشکنند. [یادداشت‌های انتشار](https://github.com/vitejs/vite/releases/tag/v8.4.0) هر تغییر را با شمارهٔ PR فهرست می‌کنند اما توضیح کمی دارند؛ این نوشته آن‌ها را بر اساس اثرشان روی پروژهٔ شما مرتب می‌کند.

## دسترسی سخت‌گیرانه‌تر به فایل‌ها: `server.fs.strict: 'extended'`

گزینهٔ `server.fs.strict` [از Vite 2.7](https://vite.dev/config/server-options) به‌صورت پیش‌فرض `true` بوده و سرو فایل‌های خارج از ریشهٔ workspace را محدود می‌کند. در 8.4 نوع آن `boolean | 'extended'` است. طبق مستندات، مقدار `'extended'` بررسی‌های دسترسی را به ماژول‌هایی که پلاگین‌ها بارگذاری می‌کنند هم تعمیم می‌دهد، به‌جز شناسه‌هایی که با `\0` شروع می‌شوند.

نکتهٔ جالب همین شکاف است. بررسی‌های کلاسیک `server.fs` از URLهایی محافظت می‌کردند که مرورگر می‌تواند درخواست کند (`/@fs/...`). پلاگینی که خودش فایلی را resolve یا load می‌کرد، پیش‌تر از همان فیلتر نمی‌گذشت؛ پس شناسهٔ ماژولی که از راه پلاگین در دسترس بود، مسیر دیگری به همان بایت‌ها بود. `'extended'` این مسیر را می‌بندد.

```ts
// vite.config.ts
import { defineConfig } from "vite";

export default defineConfig({
    server: {
        fs: {
            strict: "extended",
            // allow replaces workspace auto-detection, so list what you need
            allow: ["."],
        },
    },
});
```

نکاتی از [مستندات گزینه‌های server](https://vite.dev/config/server-options):

- تنظیم `allow` تشخیص خودکار workspace را غیرفعال می‌کند. در monorepo به‌جای جایگزین کردن، پیش‌فرض را با `searchForWorkspaceRoot` گسترش دهید.
- `server.fs.deny` بر `allow` اولویت دارد و تنظیم آن فهرست پیش‌فرض را کامل جایگزین می‌کند (`.env`، `.env.*`، پسوندهای کلید و گواهی، `.npmrc`، `.yarnrc.yml` و `**/.git/**`). پیش‌فرض‌هایی را که هنوز می‌خواهید کپی کنید.
- فیلتر deny روی شناسهٔ ماژول و همان شناسه بدون query بررسی می‌شود. پلاگین‌ها می‌توانند از طریق symlink یا مسیرهای دیگر به فایل ممنوع برسند، پس مسیرهای جایگزین را هم به deny اضافه کنید.

changelog همچنین می‌گوید ثبت ارجاع‌های safe module اکنون فقط برای `strict: 'extended'` انجام می‌شود ([#24206](https://github.com/vitejs/vite/issues/24206))، پس اگر فعالش نکنید این سازوکار جدید دخالتی ندارد.

### `environment.addSafeModule`

کنار این گزینه، 8.4 متد `environment.addSafeModule` را اضافه می‌کند ([#23974](https://github.com/vitejs/vite/issues/23974)) و `safeModulePaths` اکنون برای هر environment جداست ([#23973](https://github.com/vitejs/vite/issues/23973)). یادداشت‌ها می‌گویند ارجاع‌های بیشتر و ارجاع‌ها در HTML هم به‌عنوان safe module ثبت می‌شوند ([#23168](https://github.com/vitejs/vite/issues/23168)، [#23169](https://github.com/vitejs/vite/issues/23169)). برداشت من، که صفحهٔ انتشار صریح نمی‌گوید: این راهی است که پلاگین به Vite می‌گوید فایلی که تولید یا resolve کرده در بررسی extended مجاز است. اگر پلاگینی می‌نویسید که فایل‌هایی از بیرون ریشه سرو می‌کند (assetهای تولیدشده، ذخیرهٔ پشتیبان فایل‌های مجازی)، پیش از اینکه کاربران `'extended'` را روشن کنند آن را تست کنید و امضای دقیق فراخوانی را از PR بخوانید، نه حدس بزنید.

## bundled dev mode اکنون در SSR کار می‌کند

[#21626](https://github.com/vitejs/vite/issues/21626) استفاده از bundled dev mode را در SSR ممکن می‌کند. سخت‌تر شدن قبلی این حالت را در [نوشتهٔ 8.3.5](/fa/blog/2026-10-22-vite-8-3-5-bundled-dev) بررسی کردیم؛ این همان قطعهٔ گمشده برای نویسندگان فریم‌ورک است. چند رفع اشکال مرتبط هم در همین انتشار هست: lazy chunkها اکنون زیر `base` درست بارگذاری می‌شوند ([#23798](https://github.com/vitejs/vite/issues/23798)) و dev runtime مربوط به Rolldown به‌صورت یک فایل سرو می‌شود ([#23587](https://github.com/vitejs/vite/issues/23587)).

من در روز انتشار آن را در محیط dev یک اپ production روشن نمی‌کنم. یادداشت‌ها benchmark نمی‌دهند و حالتی که شیوهٔ سرو ماژول‌ها را در dev عوض می‌کند معمولاً اول فرض‌های پلاگین‌ها را رو می‌کند. روی یک branch امتحانش کنید و رفتار dev را با build روی entry مربوط به SSR مقایسه کنید.

## تغییرات config که می‌توانند بشکنند

پیش از بالا بردن نسخه، این موارد را جست‌وجو کنید:

| تغییر | PR |
| --- | --- |
| حذف `optimizeDeps.rollupOptions` | [#23760](https://github.com/vitejs/vite/issues/23760) |
| جایگزینی `css.devSourcemap` با `dev.sourcemap.css` | [#23765](https://github.com/vitejs/vite/issues/23765) |
| پایدار شدن `--configLoader` و منسوخ شدن `--configLoader=runner` | [#23714](https://github.com/vitejs/vite/issues/23714) |
| CSS دیگر به‌صورت پیش‌فرض externalize نمی‌شود، از جمله در SSR | [#24075](https://github.com/vitejs/vite/issues/24075) |

مورد اول شکست واقعی است. صفحهٔ انتشار حذف را زیر refactor فهرست کرده و نمی‌گوید جایگزینش چیست؛ پیش از ارتقا گزینه‌های فعلی optimizer وابستگی‌ها را در مستندات Vite بررسی کنید و نام جدید را حدس نزنید. یک جست‌وجوی ساده سریع جواب می‌دهد:

```bash
grep -rn "optimizeDeps" vite.config.* nuxt.config.* 2>/dev/null
grep -rn "devSourcemap" . --include="vite.config.*" --exclude-dir=node_modules
```

مورد `dev.sourcemap.css` به‌عنوان جایگزین `css.devSourcemap` توصیف شده است. مسیر گزینه به `dev: { sourcemap: { css: true } }` اشاره دارد، اما پیش از تکیه بر آن، شکلش را در مستندات تأیید کنید.

مورد `--configLoader` خبر خوب آرام است: این فلگ اکنون پایدار است و `runner` منسوخ شده. اگر CI یا اسکریپت‌هایتان `--configLoader=runner` می‌دهند، همین حالا که فقط deprecation است کنارش بگذارید.

## رفع اشکال‌های build و CSS که ارزش دیدن دارند

چند رفع اشکال مشکلاتی را هدف می‌گیرند که فقط در خروجی production دیده می‌شوند:

- inlined common chunkها وقتی `cssCodeSplit` برابر `false` است دیگر CSS را تکراری نمی‌کنند ([#24168](https://github.com/vitejs/vite/issues/24168)).
- فایل‌های CSS خالی دیگر emit نمی‌شوند ([#24059](https://github.com/vitejs/vite/issues/24059)) و importهای pure CSS chunk با مسیر نسبی تطبیق داده می‌شوند ([#24105](https://github.com/vitejs/vite/issues/24105)).
- side effectهای اسکریپت entry وقتی importer دیگری ابتدا آن را بارگذاری کند حفظ می‌شوند ([#24135](https://github.com/vitejs/vite/issues/24135)).
- build manifest اکنون worker chunkها را دارد ([#23699](https://github.com/vitejs/vite/issues/23699)) و روی build environment در دسترس است ([#23292](https://github.com/vitejs/vite/issues/23292)). اگر تگ‌های preload را از manifest می‌سازید، workerها اکنون برای آن کد دیده می‌شوند؛ مطمئن شوید ابزارتان با ورودی‌های جدید به مشکل نمی‌خورد.
- preloadهای CSS ناموفق می‌توانند دوباره تلاش شوند ([#23710](https://github.com/vitejs/vite/issues/23710)) که بعد از deployی که فایل‌های hash‌دار را جایگزین می‌کند برای تب‌های بازمانده مفید است.
- `url()` در CSS از subpath import پشتیبانی می‌کند ([#23869](https://github.com/vitejs/vite/issues/23869)).

چون حذف فایل خالی و افزوده‌های manifest خروجی build را عوض می‌کنند، فهرست فایل‌های `dist` را بین 8.3 و 8.4 در CI مقایسه کنید و به «چیزی جابه‌جا نشده» اعتماد نکنید.

## موارد کوچک‌تر

- خطاهای hook پلاگین و module hook اکنون نام پلاگین را دارند ([#24107](https://github.com/vitejs/vite/issues/24107)، [#24151](https://github.com/vitejs/vite/issues/24151)) که زمان پیدا کردن پلاگین خطادهنده را کم می‌کند.
- stack traceهای module runner با V8 هم‌راستا شده‌اند ([#23690](https://github.com/vitejs/vite/issues/23690)).
- WASM source phase imports پشتیبانی می‌شود ([#22675](https://github.com/vitejs/vite/issues/22675)) و preview فایل WASM فشرده را سرو می‌کند ([#24051](https://github.com/vitejs/vite/issues/24051)).
- کارایی: hookهای import analysis در build برای chunkهای بی‌تأثیر رد می‌شوند ([#24150](https://github.com/vitejs/vite/issues/24150))، وقتی terser استفاده نمی‌شود پلاگینش رد می‌شود ([#24149](https://github.com/vitejs/vite/issues/24149)) و source mapهای بازنویسی preload جابه‌جا می‌شوند، نه دوباره ردیابی ([#24049](https://github.com/vitejs/vite/issues/24049)). عددی منتشر نشده؛ این‌ها را جهت بدانید، نه اندازه‌گیری.
- `create-vite@9.4.0` همان روز با گزینهٔ devtools، پشتیبانی از package manager به نام Vite+ (`vp`) و Solid 2 در قالب‌های Solid منتشر شد.

## چک‌لیست ارتقا

1. در configها و پلاگین‌ها دنبال `optimizeDeps.rollupOptions`، `css.devSourcemap` و `--configLoader=runner` بگردید.
2. نسخه را بالا ببرید، build بگیرید و فهرست فایل‌های خروجی و manifest را با نسخهٔ قبلی مقایسه کنید.
3. در یک branch `server.fs.strict: 'extended'` را روشن کنید و dev server را با همهٔ پلاگین‌هایتان اجرا کنید. خطای 403 روی فایلی که پلاگین تولید کرده نشانهٔ نیاز به `addSafeModule` است.
4. SSR با bundled dev را به آزمایش جداگانه‌ای بسپارید.

بده‌بستان همان است که در سخت‌گیرانه‌تر کردن امنیت همیشه هست: `'extended'` پیش‌فرض نیست، پس تا نخواهید چیزی عوض نمی‌شود، اما اولین اجرا با آن جایی است که فرض‌های پلاگین‌ها می‌شکنند. این کار را روی branch انجام دهید، نه روزی که dev server هم‌تیمی دیگر یک فایل مجازی را سرو نمی‌کند.
