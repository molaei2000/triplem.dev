۱۴ اکتبر تیم Next.js یک به‌روزرسانی امنیتی خارج از برنامه منتشر کرد: نسخه **16.4.1** برای خط Active LTS و **15.5.28** برای Maintenance LTS. طبق [پست رسمی](https://nextjs.org/blog/nextjs-security-update-october-14-2026)، این انتشار شامل دو رفع‌ایراد است که به‌خاطر تأخیر وابستگی‌های بالادستی از انتشار سپتامبر عقب افتاده بودند. دو آسیب‌پذیری اجرای کد از راه دور (RCE) با شدت بحرانی و یک حمله منع سرویس (DoS) با شدت بالا رفع شده‌اند. برای مشکلات سطح فریم‌ورک راه‌حل جایگزینی وجود ندارد، پس این انتشار از نوع «همین حالا به‌روز کنید» است.

```bash
npm install next@16.4.1   # 16.x
npm install next@15.5.28  # 15.5.x
```

## سه توصیه‌نامه امنیتی

| توصیه‌نامه | شدت | نسخه‌های آسیب‌پذیر | رفع‌شده در |
| --- | --- | --- | --- |
| [GHSA-673q-mjm6-r5xr](https://github.com/vercel/next.js/security/advisories/GHSA-673q-mjm6-r5xr): RCE از طریق `use cache` که typed array برمی‌گرداند | بحرانی (CVSS v4 9.5) | 16.0.0 – 16.4.0 | 16.4.1 |
| [GHSA-2464-fhr4-w9xw](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw) / CVE-2026-96889: RCE در Image Optimization با SVG | بحرانی (CVSS v4 9.5) | 10.0.0 – 15.5.27 و 16.0.0 – 16.4.0 | 15.5.28 و 16.4.1 |
| [GHSA-p3m5-59mp-jv5r](https://github.com/vercel/next.js/security/advisories/GHSA-p3m5-59mp-jv5r): DoS در App Router با Server Actions | بالا (CVSS v4 8.2) | 13.0.0 – 15.5.27 و 16.0.0 – 16.4.0 | 15.5.28 و 16.4.1 |

به شکل بازه‌ها دقت کنید. باگ `use cache` فقط در خط 16 وجود دارد، چون Cache Components مربوط به نسخه 16 است. دو مورد دیگر سال‌ها به عقب می‌روند، پس نسخه‌های قدیمی‌تری که دیگر وصله نمی‌گیرند آسیب‌پذیرند و رفعی برایشان نیست. توصیه‌نامه‌ها فقط نسخه‌های وصله‌شده بالا را فهرست می‌کنند؛ اگر روی 14.x یا یک 15.x وصله‌نشده هستید، تنها راه مهاجرت به یک خط پشتیبانی‌شده است.

## ۱. RCE در توابع `use cache` که typed array برمی‌گردانند

این مورد مخصوص App Router با Cache Components است. طبق توصیه‌نامه، برنامه‌ای آسیب‌پذیر است که تابع `use cache` داشته باشد و **چند typed array** برگرداند. پست Next.js یک توصیه‌نامه بالادستی مرتبط در React هم لینک می‌کند، [GHSA-xqc2-xf4c-x3h3](https://github.com/react/react/security/advisories/GHSA-xqc2-xf4c-x3h3)، که آن را نخوانده‌ام و درباره محتوایش حرفی نمی‌زنم.

الگویی که باید جست‌وجو کنید چنین شکلی دارد:

```ts
// Hypothetical shape of an affected function (16.0.0 – 16.4.0)
export async function getBuffers() {
    "use cache";
    return {
        a: new Uint8Array(await loadA()),
        b: new Float32Array(await loadB()),
    };
}
```

عمداً سازوکار بهره‌برداری را توضیح نمی‌دهم: توصیه‌نامه نمی‌دهد و حدس نمی‌زنم. نکته عملیاتی همان توصیه پست است: **حتی اگر برنامه شما چنین تابعی ندارد، فوراً به‌روز کنید.** هیچ راه‌حل جایگزینی ذکر نشده، پس اثبات «من در امانم» با بررسی کد جای وصله را نمی‌گیرد. توابع کش‌شده می‌توانند در وابستگی‌ها یا کد تولیدشده هم باشند، برای همین جست‌وجو نشانه منفی قابل‌اتکایی نیست.

## ۲. RCE در Image Optimization هنگام کار با SVG

ریشه مشکل بیرون از Next.js است. پست یک آسیب‌پذیری مرتبط با حافظه در یک کتابخانه بالادستی Image Optimization را توصیف می‌کند که وقتی Next.js روی **لینوکس مبتنی بر glibc** اجرا شود می‌تواند به اجرای کد از راه دور برسد. عنوان توصیه‌نامه آن را به SVG مربوط می‌کند و احراز هویت لازم نیست.

راه‌حل جایگزین جالب است، چون یک pin وابستگی است نه یک گزینه پیکربندی:

- مطمئن شوید نسخه `sharp` که Next.js استفاده می‌کند **0.35.5 یا بالاتر** است.
- ارتقای Next.js به 15.5.28 یا 16.4.1 باعث می‌شود مدیر بسته خودش `sharp` اصلاح‌شده را تأمین کند.

آنچه واقعاً resolve می‌شود را بررسی کنید، به‌ویژه در monorepo یا با overrides:

```bash
pnpm why sharp
# or
npm ls sharp
```

اگر lockfile یک `sharp` قدیمی‌تر را pin کرده یا در `package.json` یک ورودی دستی `overrides`/`pnpm.overrides` دارید، ارتقای `next` به‌تنهایی ممکن است چیزی را عوض نکند. pin را اصلاح کنید، دوباره نصب کنید و image را rebuild کنید، چون باینری native بخشی از artifact استقراری است.

شرط glibc یعنی image های Alpine/musl متفاوت از Debian/Ubuntu توصیف می‌شوند. این را نشانه امنیت نگیرید: توصیه‌نامه شرط بهره‌برداری را می‌گوید، اما راهنمایی ندیدم که musl را مستثنا کند، و در هر حال رفع، یک ارتقای ساده است.

## ۳. DoS در Server Actions

درخواست‌های دست‌کاری‌شده علیه برنامه App Router که **دست‌کم یک Server Action** دارد می‌توانند مصرف CPU را به‌شدت بالا ببرند. چون این کار پردازش درخواست‌های دیگر در همان process را مسدود می‌کند، یک جریان ارزان درخواست همه کاربرانِ آن process را مختل می‌کند. برنامه‌های Pages Router و برنامه‌های بدون Server Action آسیب‌پذیر نیستند. پست یک توصیه‌نامه مرتبط در React را هم لینک می‌کند، [GHSA-h3gv-c5rc-p453](https://github.com/react/react/security/advisories/GHSA-h3gv-c5rc-p453)، که آن را هم نخوانده‌ام. توصیه‌نامه می‌گوید جز ارتقا راه‌حلی نیست.

پیامد عملی معماری است. سرور Node تک‌رشته‌ای با یک event loop، یک درخواست CPU-سوز را به مشکل دسترس‌پذیری برای همه کاربران تبدیل می‌کند. اجرای چند process یا instance اثر یک process گیرکرده را محدود می‌کند، اما باگ را رفع نمی‌کند و حمله مداوم می‌تواند همه را اشغال کند.

## چه باید کرد

1. **ارتقا بدهید و lockfile را بررسی کنید.** `pnpm why next` را در هر workspace اجرا کنید؛ monorepo ها اغلب بیش از یک نسخه pin می‌کنند.
2. **`sharp` را جداگانه بررسی کنید**، همان‌طور که بالا گفته شد.
3. **همه محیط‌ها را دوباره deploy کنید**، از جمله preview و branch deploy ها که تا rebuild نشوند کد قدیمی را سرو می‌کنند.
4. **image های کانتینر را rebuild کنید** تا باینری جدید `sharp` داخلشان باشد، نه اینکه image قدیمی را restart کنید.
5. **آداپتر یا پلتفرم استقرار را بررسی کنید.** توصیه‌نامه‌ها فقط درباره Next.js و وابستگی‌هایش‌اند؛ هاست‌ها ممکن است به‌روزرسانی آداپتر خودشان را داشته باشند و من چیزی را در اینجا تأیید نکرده‌ام.

## مبادلات و هشدارها

- **ریتم وصله‌ها.** این دومین ماه پیاپی با رفع‌ایرادهای بحرانی در Next.js است (نگاه کنید به [انتشارهای سپتامبر](/fa/blog/2026-10-01-nextjs-september-2026-security-releases)). دو مورد از سه مشکل از اجزای بالادستی می‌آیند؛ یادآوری اینکه سطح حمله شما شامل گراف وابستگی‌های transitive است، نه فقط route های خودتان.
- **`use cache` دیگر فقط یک قابلیت عملکردی نیست.** حالا یک توصیه‌نامه بحرانی بدون راه‌حل دارد. اگر زود Cache Components را پذیرفته‌اید، به‌روزرسانی‌های patch نسخه 16 را در مسیر سریع بگذارید.
- **«بدون بهره‌برداری شناخته‌شده» در منابع نیست.** صفحاتی که خواندم نمی‌گویند این باگ‌ها در عمل بهره‌برداری شده‌اند یا نه، پس هیچ‌کدام را فرض نکنید. امتیازهای CVSS امتیاز پایه v4 هستند و استقرار شما را در نظر نمی‌گیرند.
- **میزان قرارگیری Image Optimization به پیکربندی بستگی دارد.** توصیه‌نامه نمی‌گوید محدود کردن `images.remotePatterns` یا خاموش کردن SVG باگ را کاهش می‌دهد، پس ادعایش نمی‌کنم؛ اول ارتقا بدهید، بعد پیکربندی را به‌عنوان دفاع در عمق سخت‌تر کنید.
- **نسخه‌ها.** صفحه release نسخه‌های 16.4.1 و 15.5.28 را رفع‌شده نشان می‌دهد؛ وصله‌های بعدی 16.4.x هم وجود دارند، اما موضوع جداگانه‌ای از این رفع امنیتی‌اند.

## جمع‌بندی

دو RCE بدون احراز هویت و یک DoS مبتنی بر مصرف CPU، رفع‌شده در 16.4.1 و 15.5.28. اقدام یک‌خطی ارتقاست؛ بررسی‌های تکمیلی: `pnpm why sharp` برای pipeline تصویر، rebuild هر artifact مستقرشده، و نگاه جدی به اینکه نسخه‌های major قدیمی‌تر تا کی بدون وصله می‌مانند.
