در ۷۲ ساعت گذشته جز وصله‌ها و نسخه‌های release candidate خبر مهمی نبود (Vue هنوز روی RCهای 3.6 است و آخرین نسخه‌ی پایدار 3.5.45 است)، پس امروز یک نکته‌ی کاربردی داریم درباره‌ی پیش‌فرضی که هنگام مهاجرت از Nuxt 3 دردسر می‌سازد: ref برگردانده‌شده از composableهای دریافت داده، shallow است.

## اشتباه رایج

لیستی را دریافت می‌کنید و بعد از یک کنش کاربر، یک آیتم را درجا تغییر می‌دهید، مثلاً برای به‌روزرسانی خوش‌بینانه (optimistic):

```vue
<script setup lang="ts">
const { data: todos } = await useFetch<Todo[]>("/api/todos");

function toggle(id: number) {
    const todo = todos.value?.find((t) => t.id === id);
    if (todo) todo.done = !todo.done; // درست به نظر می‌رسد، اما چیزی نشان داده نمی‌شود
}
</script>

<template>
    <label v-for="t in todos" :key="t.id">
        <input type="checkbox" :checked="t.done" @change="toggle(t.id)" />
        {{ t.title }}
    </label>
</template>
```

با `ref` عمیق این کد کار می‌کند. با پیش‌فرض فعلی، قالب دوباره رندر نمی‌شود.

## چرا این اتفاق می‌افتد

[راهنمای ارتقا به Nuxt 4](https://nuxt.com/docs/4.x/getting-started/upgrade) می‌گوید `data` در `useAsyncData`، `useFetch`، `useLazyAsyncData` و `useLazyFetch` حالا `shallowRef` است، نه `ref`. جایگزین کردن کل مقدار همچنان به‌روزرسانی را فعال می‌کند، اما تغییر یک ویژگی تو در تو نه. دلیل اعلام‌شده کارایی است: Vue دیگر لازم نیست هر ویژگی و هر عنصر آرایه‌ی تو در تو را ردیابی کند، که برای پاسخ‌های عمیق مفید است. راهنما همچنین می‌گوید معمولاً باید با `data` مثل داده‌ی تغییرناپذیر رفتار کرد.

[مرجع `useAsyncData`](https://nuxt.com/docs/4.x/api/composables/use-async-data) همین را به‌صورت یک گزینه فهرست می‌کند: `deep` به‌طور پیش‌فرض `false` است (از v3.8 اضافه شده) و برای کارایی یک shallow ref برمی‌گرداند.

بخش بد ماجرا این است که تغییر بی‌صدا رخ می‌دهد. شیء زیرین واقعاً عوض شده، پس رندر دوباره‌ای که به دلیلی نامرتبط رخ دهد می‌تواند UI را دوباره درست نشان دهد و باگ را گاه‌به‌گاه جلوه دهد.

## راه‌حل: جایگزین کنید، تغییر ندهید

مقدار دریافتی را تغییرناپذیر فرض کنید و مقدار جدید را انتساب دهید:

```ts
function toggle(id: number) {
    if (!todos.value) return;
    todos.value = todos.value.map((t) => (t.id === id ? { ...t, done: !t.done } : t));
}
```

انتساب `todos.value` جایگزینی کل مقدار است و shallow ref آن را ردیابی می‌کند. فقط آیتمِ تغییرکرده هویت جدید می‌گیرد، پس رندر لیستِ keyed بقیه‌ی ردیف‌ها را پایدار نگه می‌دارد.

اگر داده‌ی جدید روی سرور هم لازم است، نوشتن را با یک فراخوانی API انجام دهید و بعد `refresh()` را صدا بزنید، نه اینکه نسخه‌ی محلی را ویرایش کنید. جایگزینی محلیِ بالا برای UI خوش‌بینانه است و باید بعداً با پاسخ سرور همگام شود.

## وقتی واقعاً واکنش‌پذیری عمیق می‌خواهید

اگر یک فراخوانی خاص را چیزی مصرف می‌کند که فیلدهای تو در تو را درجا ویرایش می‌کند، مثلاً فرمی که با `v-model` به `data.value.profile.name` بسته شده، فقط برای همان فراخوانی فعالش کنید:

```ts
const { data: profile } = await useFetch("/api/profile", { deep: true });
```

راهنمای ارتقا این فعال‌سازی تکی را به‌عنوان گزینه‌ی اول نشان می‌دهد. یک کلید سراسری برای کل پروژه هم مستند کرده، اما می‌گوید توصیه نمی‌شود:

```ts
export default defineNuxtConfig({
    experimental: {
        defaults: {
            useAsyncData: {
                deep: true,
            },
        },
    },
});
```

راهنما یک codemod هم برای مهاجرت ذکر می‌کند: `npx codemod@latest nuxt/4/shallow-function-reactivity`. من آن را اجرا نکرده‌ام، پس قبل از commit تغییراتش را مرور کنید.

## مصالحه‌ها و نکات

**عمیق یا shallow یک تصمیم هزینه است.** ref عمیق اشیای تو در تو را در proxyهای واکنش‌پذیر می‌پیچد و هر خواندن ویژگی را ردیابی می‌کند. برای یک شیء کوچک تنظیمات این هزینه بی‌اهمیت است. برای لیست بزرگی از رکوردهای تو در تو، در هر دریافت و هنگام hydration کار واقعی است. پیش‌فرض shallow دقیقاً همین حالت را هدف گرفته، پس فعال کردن سراسری deep این مزیت را پس می‌دهد.

**جایگزین بهتر برای `deep: true` اغلب یک کپی محلی است.** اگر فرم قابل ویرایش لازم دارید، داده را هنگام رسیدن در یک `ref` (یا `reactive`) محلی کپی کنید و آن را ویرایش کنید. مقدار دریافتی یک snapshot تغییرناپذیر می‌ماند و state فرم صاحب روشنی دارد. این کار از یک مشکل ظریف هم جلوگیری می‌کند: تغییر درجای `data` شیء کش‌شده را عوض می‌کند و مصرف‌کنندگان دیگرِ همان کلید ممکن است آن را بخوانند.

**کلیدهای مشترک باید هم‌نظر باشند.** مرجع می‌گوید `deep` باید در همه‌ی فراخوانی‌های `useAsyncData` که کلید مشترک دارند یکسان باشد و ناهماهنگی در حالت توسعه هشدار می‌دهد. اگر یک کامپوننت `deep: true` می‌خواهد و دیگری همان کلید را shallow می‌خواند، کلیدها را جدا کنید یا ویرایش را به یک کپی محلی ببرید.

**`default` و `clear()` از همین قاعده پیروی می‌کنند.** گزینه‌ی `default` یک factory است که پیش از resolve شدن فراخوانی، مقدار `data` را می‌دهد و `clear()` در صورت وجود `default`، `data` را به `default()` برمی‌گرداند. از factory شیء تازه برگردانید، نه یک ثابت مشترک در سطح ماژول، تا یک مصرف‌کننده نتواند مقدار اولیه‌ی دیگری را تغییر دهد.

**جایگزینی هنوز مسیر ارزان است.** `refresh()` و `watch: [...]` کل `data` را جایگزین می‌کنند، که دقیقاً همان به‌روزرسانی‌ای است که shallow ref برایش ساخته شده. برای تغییرات مبتنی بر سرور کد اضافه‌ای لازم نیست. فقط ویرایش‌های درجا در سمت کلاینت توجه می‌خواهند.

## وقتی الگوی اول هنوز خوب است

اگر پاسخی کوچک و تخت دارید که یک کامپوننت ویرایشش می‌کند و هیچ چیز دیگری نمی‌خواندش، `deep: true` روی همان یک فراخوانی انتخابی معقول و خوانا است. نکته این است که این انتخاب را برای هر فراخوانی آگاهانه بکنید، نه اینکه پس از ارتقا از UIای که به‌روز نمی‌شود کشفش کنید.

## چک‌لیست مرور سریع

بعد از رفتن به Nuxt 4 در کدبیس دنبال این شکل‌ها بگردید:

- `data.value.something = ...` یا `data.value.items.push(...)` بعد از دریافت
- `v-model` بسته به مسیری درون `data`
- `watch(data, ..., { deep: true })` برای گرفتن تغییرات تو در تو (روی shallow ref آن‌ها را نمی‌بیند)

هرکدام یا جایگزینی‌ای است که باید نوشته شود، یا کپی محلی‌ای که باید ساخته شود، یا فراخوانی‌ای که باید `deep: true` را صریح بگوید.
