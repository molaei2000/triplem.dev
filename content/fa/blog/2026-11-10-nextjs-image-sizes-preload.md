دو عادت در `next/image` از code review رد می‌شوند چون چیزی را خراب نمی‌کنند: تصویر `fill` در یک شبکه‌ی کارت‌ها بدون `sizes`، و تبدیل مکانیکی `priority` به `preload` هنگام ارتقا به Next.js 16. هر دو تغییر می‌دهند که مرورگر چه چیزی و کی دانلود کند. هیچ‌کدام خطا نمی‌دهند؛ فقط LCP بدتر و تب network سنگین‌تر می‌شود.

همه‌ی موارد زیر با [مرجع فعلی `next/image`](https://nextjs.org/docs/app/api-reference/components/image) (آخرین به‌روزرسانی: 2026-11-06) تطبیق داده شده است.

## اشتباه اول: `fill` بدون `sizes`

```tsx
// app/components/product-card.tsx
import Image from "next/image";

export function ProductCard({ src, name }: { src: string; name: string }) {
    return (
        <div className="relative aspect-4/3">
            {/* In a 3-column grid, each card is about a third of the viewport. */}
            <Image fill src={src} alt={name} />
        </div>
    );
}
```

مستندات می‌گویند اگر `sizes` نباشد، مرورگر فرض می‌کند تصویر به پهنای viewport (`100vw`) است و ممکن است فایلی بی‌جهت بزرگ دانلود کند. کامپوننت بسته به ورودی‌ها، ساخت `srcset` را هم تغییر می‌دهد:

- `width` تنظیم شده، بدون `sizes`: یک `srcset` محدود (مستندات 1x و 2x را مثال می‌زنند)، مناسب تصاویر با اندازه‌ی ثابت.
- `fill` بدون `sizes`: `srcset` فقط از `deviceSizes` ساخته می‌شود، انگار تصویر کل viewport را می‌پوشاند.
- با `sizes`: یک `srcset` کامل با توصیف‌گر عرض (640w، 750w و ...) برای چینش‌های واکنش‌گرا.

پس در شبکه‌ی بالا، کارتی که روی صفحه‌ی عریض یک‌سوم عرض را دارد، از مرورگر می‌خواهد برای یک جایگاه تمام‌عرض کاندیدا انتخاب کند. مرورگر همان کاری را می‌کند که گفته‌اید. هزینه‌اش را صفحه با بایت می‌دهد، و در تصاویر LCP با زمان.

### راه‌حل

چینش را همان‌طور توصیف کنید که CSS شما می‌کند: اول شرط‌های media و در آخر مقدار پیش‌فرض:

```tsx
<Image
    fill
    src={src}
    alt={name}
    sizes="(max-width: 768px) 100vw, (max-width: 1200px) 50vw, 33vw"
/>
```

مستندات می‌گویند وقتی تصویر `fill` است یا CSS آن را واکنش‌گرا می‌کند، سراغ `sizes` بروید. مقدار باید با چینش واقعی شما یکی باشد. اگر شبکه در یک breakpoint جدید چهار ستونه شود و `sizes` هنوز `33vw` بگوید، مرورگر بی‌صدا کاندیدایی بیش از حد بزرگ یا کوچک برمی‌دارد. با `sizes` مثل نسخه‌ی دوم جدول breakpointها رفتار کنید و آن را کنار CSS مربوطه، ترجیحاً در همان کامپوننت، نگه دارید.

### `imageSizes` اینجا چه می‌کند

وقتی `sizes` داده شود، Next.js `srcset` را از الحاق `imageSizes` و `deviceSizes` می‌سازد. مرجع یادآوری می‌کند که `imageSizes` فقط برای تصاویری استفاده می‌شود که `sizes` دارند و همه‌ی مقادیرش باید از کوچک‌ترین مقدار `deviceSizes` کوچک‌تر باشند. اگر طراحی شما تصاویر بندانگشتی کوچک، مثلاً ۴۸ یا ۹۶ پیکسل، دارد، این عرض‌ها به `imageSizes` تعلق دارند. بندانگشتی بدون `sizes` هرگز از آن‌ها استفاده نمی‌کند.

## اشتباه دوم: `preload` را جایگزین مستقیم `priority` دانستن

مرجع می‌گوید از Next.js 16، `priority` به نفع `preload` منسوخ شده تا رفتار روشن‌تر باشد. جدول نسخه‌ها این را در `v16.0.0` ثبت کرده: prop به نام `preload` اضافه و `priority` منسوخ شد. پس تشویق به ارتقا واقعی است.

اما ببینید `preload` دقیقاً چه می‌کند. با مقدار `true`، یک `<link>` در `<head>` سند درج می‌کند تا تصویر از پیش بارگذاری شود. همین. مستندات می‌گویند کی منطقی است:

- تصویر عنصر LCP است؛
- بالای صفحه (above the fold) است، معمولاً hero؛
- می‌خواهید بارگذاری از `<head>` شروع شود، پیش از آنکه مرورگر آن را در `<body>` کشف کند.

و کی نه:

- بسته به viewport چند تصویر می‌توانند عنصر LCP باشند؛
- از `loading` استفاده می‌کنید؛
- از `fetchPriority` استفاده می‌کنید.

جمله‌ی آخر آن بخش را به خاطر بسپارید: مستندات در بیشتر موارد `loading="eager"` یا `fetchPriority="high"` را به‌جای `preload` توصیه می‌کنند.

```tsx
// Hero whose position is stable across viewports
<Image src={hero} alt="" sizes="100vw" fetchPriority="high" loading="eager" />

// Only if the hero is genuinely discovered late and is always the LCP element
<Image src={hero} alt="" sizes="100vw" preload />
```

توجه کنید که مستندات می‌گویند `preload` را با `loading` یا `fetchPriority` ترکیب نکنید؛ برای هر تصویر یک راهبرد انتخاب کنید.

### تله‌ی art direction

الگوی رایج این است که دو تصویر رندر شود، یکی برای موبایل و یکی برای دسکتاپ، و یکی با CSS پنهان شود. مرجع برای همین یک مثال art direction دارد و تذکرش صریح است: مقدار پیش‌فرض `loading="lazy"` تضمین می‌کند فقط تصویر درست بارگذاری شود. آنجا نمی‌توان از `preload` یا `loading="eager"` استفاده کرد، چون هر دو تصویر بارگذاری می‌شوند. ابزار پیشنهادی `fetchPriority="high"` است. تبدیل کورکورانه‌ی `priority` به `preload` در چنین کامپوننتی دانلود hero را روی همه‌ی دستگاه‌ها دو برابر می‌کند.

## موازنه‌ها و جایی که الگوی قبلی درست است

- **تصویر با اندازه‌ی ثابت، با `width` و `height` و بدون `sizes`، مشکلی ندارد.** `srcset` محدود 1x/2x دقیقاً چیزی است که برای آواتاری که همیشه ۶۴ پیکسل است می‌خواهید.
- **`sizes="100vw"` روی hero واقعاً تمام‌عرض درست است** و زیرکی بیشتر سودی ندارد. مشکل `fill` بدون `sizes` فقط وقتی پیش می‌آید که جایگاه واقعی از viewport باریک‌تر باشد.
- **`preload` غلط نیست،** فقط محدودتر از چیزی است که اسم `priority` القا می‌کرد. برای یک تصویر LCP مشخص که دیر در markup می‌آید، شروع fetch از `<head>` دقیقاً همان چیزی است که می‌خواهید.
- **`sizes` یک راهنمایی است، نه قید.** مرورگر ممکن است باز هم متفاوت انتخاب کند و مستندات فقط می‌گویند مرورگر از `sizes` برای انتخاب از `srcset` تولیدشده استفاده می‌کند.

## یک ممیزی سریع

1. روی `fill` جست‌وجو کنید و ببینید هر مورد `sizes`ای دارد که با شبکه‌ی CSS یکی است.
2. روی `preload` و `priority` جست‌وجو کنید. برای هر کدام بپرسید آن تصویر در همه‌ی viewportها همیشه عنصر LCP است یا نه. اگر نیست، از `fetchPriority="high"` استفاده کنید.
3. در پنل network بزرگ‌ترین کاندیدای انتخاب‌شده را روی یک viewport متوسط ببینید. اگر عرض دانلودشده خیلی بیشتر از عرض CSS رندرشده ضرب در نسبت پیکسل دستگاه است، `sizes` غلط است یا نیست.

یادتان باشد جدول نسخه‌ی همان صفحه ثبت کرده که در Next.js 16 پیکربندی پیش‌فرض `qualities` به `[75]` تغییر کرد. اگر مقادیر دیگری برای `quality` می‌دهید، مستندات می‌گویند مقداری بیرون از فهرست `qualities` پیکربندی‌شده به نزدیک‌ترین مقدار مجاز تبدیل می‌شود و حالت توسعه هشدار می‌دهد. مقادیری را که واقعاً استفاده می‌کنید به فهرست مجاز اضافه کنید تا این تبدیل را در production کشف نکنید.
