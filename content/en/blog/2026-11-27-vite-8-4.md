Vite 8.4.0 landed on 26 November, after two betas (16 and 25 November). Unlike the 8.3.x patch stream, this is a minor with real surface area: a second level of dev-server file protection, a new per-environment API for it, bundled dev mode reaching SSR, and a few removals and renames that can break a config. The [release notes](https://github.com/vitejs/vite/releases/tag/v8.4.0) list each change by PR number but give little prose, so this post sorts them by what is likely to affect you.

## Stricter file serving: `server.fs.strict: 'extended'`

`server.fs.strict` has been `true` by default [since Vite 2.7](https://vite.dev/config/server-options), and it restricts serving files outside the workspace root. With 8.4 its type is `boolean | 'extended'`. Per the docs, `'extended'` also applies the access checks to modules loaded by plugins, with the exception of IDs starting with `\0`.

That gap is the interesting part. The classic `server.fs` checks guard the URLs a browser can request (`/@fs/...`). A plugin that resolves or loads a file by itself previously did not go through the same filter, so a module ID reachable through a plugin was a different path to the same bytes. `'extended'` closes that.

```ts
// vite.config.ts
import { defineConfig } from "vite";

export default defineConfig({
    server: {
        fs: {
            strict: "extended",
            // allow replaces workspace auto-detection, so list what you need
            allow: ["."],
        },
    },
});
```

Things worth knowing from the [server options docs](https://vite.dev/config/server-options):

- Setting `allow` disables automatic workspace detection. If you use a monorepo, extend the default with the exported `searchForWorkspaceRoot` instead of replacing it.
- `server.fs.deny` takes priority over `allow`, and setting it replaces the default list (`.env`, `.env.*`, key and certificate extensions, `.npmrc`, `.yarnrc.yml`, `**/.git/**`). Copy the defaults you still want.
- The deny filter is checked against the module ID and the ID with query parameters stripped. Plugins can reach a denied file through symlinks or other paths, so add the alternative paths too.

The changelog also notes that safe-module reference registration is now limited to `strict: 'extended'` ([#24206](https://github.com/vitejs/vite/issues/24206)), so the new machinery stays out of the way when you do not opt in.

### `environment.addSafeModule`

Alongside the option, 8.4 adds `environment.addSafeModule` ([#23974](https://github.com/vitejs/vite/issues/23974)), and `safeModulePaths` is now separate per environment ([#23973](https://github.com/vitejs/vite/issues/23973)). The notes also say more reference types and references in HTML are registered as safe modules ([#23168](https://github.com/vitejs/vite/issues/23168), [#23169](https://github.com/vitejs/vite/issues/23169)). My reading, which the release page does not spell out: this is how a plugin tells Vite that a file it generated or resolved is legitimate under the extended check. If you maintain a plugin that serves files from outside the root (generated assets, virtual-file backing stores), test it with `strict: 'extended'` before users enable it, and read the PR for the exact call signature rather than guessing it.

## Bundled dev mode now works in SSR

[#21626](https://github.com/vitejs/vite/issues/21626) makes bundled dev mode usable in SSR. We covered the earlier hardening of that mode in [the 8.3.5 post](/blog/2026-10-22-vite-8-3-5-bundled-dev); this is the piece that was missing for framework authors. Related fixes in the same release touch the mode: lazy chunks now load correctly under `base` ([#23798](https://github.com/vitejs/vite/issues/23798)), and the Rolldown dev runtime is served as a single file ([#23587](https://github.com/vitejs/vite/issues/23587)).

I would not turn this on in a production app's dev setup on the day of release. The notes give no benchmarks, and a mode that changes how modules are served in dev tends to surface plugin assumptions first. Try it on a branch, and compare dev-versus-build behaviour on your SSR entry.

## Config changes that can break you

These are the items I would grep for before bumping the version:

| Change | PR |
| --- | --- |
| `optimizeDeps.rollupOptions` removed | [#23760](https://github.com/vitejs/vite/issues/23760) |
| `css.devSourcemap` replaced by `dev.sourcemap.css` | [#23765](https://github.com/vitejs/vite/issues/23765) |
| `--configLoader` stable, `--configLoader=runner` deprecated | [#23714](https://github.com/vitejs/vite/issues/23714) |
| CSS no longer externalized by default, including SSR | [#24075](https://github.com/vitejs/vite/issues/24075) |

The first one is the real break. The release page lists the removal as a refactor and does not say what replaces it, so check the Vite docs for the current dependency-optimizer options before upgrading rather than assuming a rename. A plain search finds it fast:

```bash
grep -rn "optimizeDeps" vite.config.* nuxt.config.* 2>/dev/null
grep -rn "devSourcemap" . --include="vite.config.*" --exclude-dir=node_modules
```

The `dev.sourcemap.css` entry is described as a replacement for `css.devSourcemap`. The option path suggests `dev: { sourcemap: { css: true } }`, but confirm the shape in the docs before relying on it.

The `--configLoader` item is the quiet good news: the flag is now stable, and `runner` is deprecated. If your CI or scripts pass `--configLoader=runner`, move off it now while it is only a deprecation.

## Build and CSS fixes worth a look

Several fixes target problems that show up only in production output:

- Inlined common chunks no longer duplicate CSS when `cssCodeSplit` is `false` ([#24168](https://github.com/vitejs/vite/issues/24168)).
- Empty CSS files are no longer emitted ([#24059](https://github.com/vitejs/vite/issues/24059)), and pure CSS chunk imports match by relative path ([#24105](https://github.com/vitejs/vite/issues/24105)).
- Entry script side effects survive when another importer loads the script first ([#24135](https://github.com/vitejs/vite/issues/24135)).
- The build manifest now includes worker chunks ([#23699](https://github.com/vitejs/vite/issues/23699)) and is exposed on the build environment ([#23292](https://github.com/vitejs/vite/issues/23292)). If you generate preload tags from the manifest, workers are now visible to that code, so check that your tooling does not choke on the new entries.
- Failed CSS preloads can be retried ([#23710](https://github.com/vitejs/vite/issues/23710)), which helps after a deploy replaces hashed files under a long-lived tab.
- CSS `url()` supports subpath imports ([#23869](https://github.com/vitejs/vite/issues/23869)).

Because empty-file removal and the manifest additions change build output, diff your `dist` listing between 8.3 and 8.4 in CI instead of trusting that nothing moved.

## Smaller items

- Plugin hook and module-hook errors now include the plugin name ([#24107](https://github.com/vitejs/vite/issues/24107), [#24151](https://github.com/vitejs/vite/issues/24151)), which cuts the time spent finding which plugin threw.
- Module runner stack traces are aligned with V8 ([#23690](https://github.com/vitejs/vite/issues/23690)).
- WASM source phase imports are supported ([#22675](https://github.com/vitejs/vite/issues/22675)), and preview serves compressed WASM ([#24051](https://github.com/vitejs/vite/issues/24051)).
- Performance: build import analysis hooks skip unaffected chunks ([#24150](https://github.com/vitejs/vite/issues/24150)), the terser plugin is skipped when terser is not used ([#24149](https://github.com/vitejs/vite/issues/24149)), and preload-rewrite source maps are shifted rather than re-traced ([#24049](https://github.com/vitejs/vite/issues/24049)). No numbers were published, so treat these as direction, not measurement.
- `create-vite@9.4.0` shipped the same day with a devtools option, support for the Vite+ (`vp`) package manager and Solid 2 in the Solid templates.

## Upgrade checklist

1. Search configs and plugins for `optimizeDeps.rollupOptions`, `css.devSourcemap` and `--configLoader=runner`.
2. Bump, build, and diff the output file list and manifest against the previous version.
3. Opt into `server.fs.strict: 'extended'` in a branch and run your dev server with every plugin you use. A 403 on a file a plugin generates is the signal that it needs `addSafeModule`.
4. Leave SSR bundled dev for a separate experiment.

The trade-off is the usual one for security tightening: `'extended'` is not the default, so nothing changes until you ask for it, but the first run with it on is where plugin assumptions break. Do that on a branch, not on the day a teammate's dev server stops serving a virtual file.
