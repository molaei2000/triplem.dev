[Nuxt v4.7.0](https://github.com/nuxt/nuxt/releases/tag/v4.7.0) landed on 23 November, roughly 350 commits after 4.6.4 according to the [release post](https://nuxt.com/blog/v4-7). Most of it is opt-in or experimental, but a few items change behaviour by default, and one is a security fix that may need action outside your repository. This post goes through what matters for production apps.

## Do this first: the `_payload.json` advisory

The release notes list a medium-severity issue, [GHSA-jxc9-w3j6-pwp2](https://github.com/nuxt/nuxt/security/advisories/GHSA-jxc9-w3j6-pwp2). If a wildcard `cache`, `swr` or `isr` route rule is combined with a more specific rule for a page, one user's page data could be cached and served to another. The typical shape is a broad cached rule plus `cache: false` on an authenticated section:

```ts
export default defineNuxtConfig({
  routeRules: {
    "/**": { swr: 60 },
    "/account/**": { cache: false },
  },
});
```

Upgrading fixes the server. It does not clear anything already stored, so the notes advise purging any CDN or edge cache that may hold `_payload.json` files if those rules cover user-specific pages.

The same release fixes an incomplete earlier fix for encoded slashes on catch-all routes ([GHSA-vrh2-cfcx-c3fg](https://github.com/nuxt/nuxt/security/advisories/GHSA-vrh2-cfcx-c3fg), medium; it affects rules like `appMiddleware` on `pages/[...slug].vue`) and a low-severity dev-server runtime-config exposure ([GHSA-h5xj-x893-p5f7](https://github.com/nuxt/nuxt/security/advisories/GHSA-h5xj-x893-p5f7)). The notes say four issues are fixed but list three, with advisories published on 24 November, so re-check the advisory page.

## Nitro v3, by adding one dependency

You can now build a Nuxt 4 app on Nitro v3, the base of Nuxt 5. There is no config flag: add `nitro` to your dependencies and Nuxt uses it; remove it to go back to v2. The release calls it "highly experimental" and recommends a branch, not production.

On Nuxt 4, v3 runs behind a compatibility layer, `nitroLegacy`, that keeps `h3` and `nitropack` imports, v2 auto-imports, `useRuntimeConfig(event)`, `event.node` and v2 hooks working. Once things run, turn it off to find code that still leans on it:

```ts
export default defineNuxtConfig({
  nitroLegacy: false,
});
```

Three breaking points to check:

- **Wildcards match more.** `/blog/*` now also matches `/blog/2026/hello`. Nuxt warns (`NUXT_B4029`) for each rule whose meaning changes. A rule with several wildcards, such as `/api/*/items/**`, fails the build; rewrite it with a named parameter: `/api/:id/items/**`.
- **Matching is shared.** The app matches route rules the way the server does, so Nuxt-only rules (`appMiddleware`, `ssr`) apply to the same paths in both places.
- **No fallback to Nuxt's dependencies.** If server code imports a package missing from your `package.json`, `nuxt dev` fails with something like `Cannot find package 'ufo'`. Declare everything the server imports.

The published numbers (same app, about 170 pages, identical HTML) are 926 to 1,236 req/s on the home page (+33%) and 219 to 316 req/s on a page with 1,000 links (+44%). The release doesn't describe the load-test setup, so treat those as directional and measure your own routes.

## Validated `runtimeConfig`

Any `runtimeConfig` value can now be a Standard Schema (Zod, ArkType, Valibot):

```ts
import { z } from "zod";

export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: z.string(), // required at runtime
    public: {
      mode: z.enum(["preview", "production"]).default("production"),
    },
  },
});
```

Environment variables are coerced to the schema's types at server start, and if anything is missing or invalid the server refuses to start with one `NUXT_E8014` error listing every problem. The schema is compiled to a small description at build time and is not shipped in the server bundle. The supported validations are intentionally limited for now (types, required values, enums, unions) to keep startup fast, so check that the rules you rely on are among them.

It builds on [an earlier tip about runtimeConfig and env vars](/blog/2026-11-13-nuxt-runtime-config-env): a bad or missing value now stops the server at boot instead of surfacing later, which suits a container orchestrator.

## Server-side `NuxtErrorBoundary`

With `experimental.ssrErrorBoundary` (included in `compatibilityVersion: 5`), `<NuxtErrorBoundary>` catches errors thrown during server rendering. A broken child renders the `#error` slot in place, the response stays a 200 and the client hydrates to the same state. In production, non-HTTP errors reach the slot as a plain 500, so messages don't leak into the HTML.

```vue
<NuxtErrorBoundary retry-on-client>
  <template #error="{ error, clearBoundaryError }">
    <p>Recommendations are unavailable.</p>
    <button @click="clearBoundaryError">Retry</button>
  </template>
  <RecommendationsPanel />
</NuxtErrorBoundary>
```

`retry-on-client` renders the fallback in the HTML, then retries the real content in the browser, and replaces the now-deprecated `<NuxtClientFallback>`. The slot prop `clearError` is renamed `clearBoundaryError`, so you can't accidentally call the global `clearError`, which would leave the boundary broken. The trade-off: a 200 with a fallback hides failures from status-code monitoring, so log inside the boundary.

## Performance work

The headline numbers compare v4.6.4 with v4.7.0 on the starter app from the e18e framework benchmarks, plus Nuxt's own apps:

| Metric | 4.6.4 | 4.7.0 |
| --- | --- | --- |
| Server output (starter) | 2.17 MB | 1.23 MB |
| Initial page load (starter) | 80.4 kB, 14 requests | 66.3 kB, 3 requests |
| SSR throughput (starter) | 245 req/s | 292 req/s |
| Total blocking time (Nuxt UI landing page) | 276 ms | 180 ms |

Build time is about 7% faster on the large app and about 6% slower on the starter. The load-testing setup isn't described beyond this. The mechanisms are more useful than the numbers:

- **`experimental.staticRoutes`** builds the vue-router matcher once instead of per request. The catch: `router.addRoute()`, `removeRoute()` and `clearRoutes()` throw, so add routes through the `pages:extend` hook.
- **Lighter client:** `ofetch` is dropped when nothing uses `$fetch`, and unhead when the client never touches head. Static internal `<NuxtLink>`s compile to plain anchors in production.
- **Hydration:** V8 compile hints on entry, layout and page chunks, with yielding between boot phases.
- **Parallel builds:** `experimental.viteEnvironmentApi` builds client and server together, and `experimental.parallelBuild: false` opts out if a plugin reads client output during the server build.

## Developer experience

- **Template diagnostics** (on by default) warn about `<NuxtLink to="/abuot">` matching no page (`NUXT_B4025`) and about `v-on`/`v-model` or functions passed to server components (`NUXT_B3014`, `NUXT_B3015`). Links to server routes, `public/` files or other sites need the `external` prop.
- **The dev error badge** now also gathers type errors, ESLint output and Vue compiler warnings. `typescript.typeCheck` accepts `'dev'` or `'build'`, useful if CI already runs `nuxt typecheck`.
- **Nuxt CLI 4.1** renders the production build itself, and `nuxt dev --https` serves HTTP/2.
- **`@nuxt/rsbuild-builder`** (`builder: 'rsbuild'`) replaces the deprecated `@nuxt/rspack-builder`.

## WebMCP, experimental

Behind `experimental.webmcp`, a `@tool` JSDoc tag on a function exposes it to in-browser AI agents through WebMCP, a proposed browser API. Arguments come from the template, so an agent can only do what a user could click, and a disabled button can't be triggered. The spec is still moving and it's in early Chrome preview behind a flag; other browsers register nothing and the app behaves as before. Interesting, but not something to ship yet.

## Upgrade checklist

```sh
npx nuxt upgrade --dedupe
```

- Nuxt 4.7 requires `vue` `^3.5.46`; older versions trigger `NUXT_B7042`.
- `@nuxt/devtools` is no longer installed with Nuxt. Add it to `devDependencies` if you use it.
- `globalThis.$fetch` is only installed on the client when the build detects use. If you call it from inline scripts or `public/` files, set `experimental.globalFetch: true`.
- Expect new `NUXT_B4025` warnings from template diagnostics.
- If you use `cache`, `swr` or `isr` rules with user-specific pages, purge `_payload.json` from any CDN.

Try Nitro v3 on a branch, with `nitroLegacy` on first, and read the "Testing Nitro v3" section of the upgrade guide before you do.
